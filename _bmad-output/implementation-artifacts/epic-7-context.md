# Epic 7 Context: Approve the fix and the orders go through

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

This epic is the climax of the two-minute demo. When a diagnosis finds a data-format cause, OcuTalon proposes repair and resend, works out a dry run that changes nothing, raises one approval request whose targets are fixed, and carries that request on the incident notice. After approval it re-checks each target, resends repaired copies, leaves the originals untouched and reports how many went through ("All 50 orders went through."), for at least 500 messages. It never retries a failed resend, or acts on a changed target, without a new approval, and a resend cut short by a restart says how far it got. This turns Epic 5's diagnosed incident into an approved fix you can audit, moving the incident through awaiting approval, fixing and resolved.

## Stories

- Story 7.1: Repair and resend proposes a dry run that changes nothing (done)
- Story 7.2: The incident notice carries the dry run and one approval request
- Story 7.3: Approved repairs are re-checked and resent
- Story 7.4: OcuTalon reports how many orders went through
- Story 7.5: A resend cut short by a restart says how far it got

## Requirements & Constraints

- **A repair is narrow.** It reformats one field with a reformatter registered in code (a date pattern or number format from a fixed set). The model picks only the kind and its parameters (field, source format, target format); no model-written code runs. A reformatter refuses a value that doesn't match its source format and never evaluates its input.
- **The dry run changes nothing.** It reports the affected count, one before-and-after example, what will be resent, and how many it left out because their field couldn't be read. A snapshot test of message headers and bodies, production and item settings, and queues in OCUTALON and OCUORDERS finds no change. The CI mock receives no request during a dry run, nor during an execution.
- **Targets are fixed when the request is raised.** Carrying it out calls no model. Each target is re-checked first (still failed, not resent, body unchanged, still in the request's scope); a changed one is skipped with a plain reason and never acted on without a new approval.
- **The originals stay unchanged.** Each copy stays in its original's trace session, with the same `SuperSession`.
- **A copy that fails again** is reported, never retried without a new approval, and counts against the fix: it never opens a new failure group or incident.
- **One `result` notification per run**, so every channel gets the same result at once. One OcuTalon `Action` audit entry sits beside IRIS's own resend entries and holds no key, token, password or Telegram identity.
- **Scale.** One request covers at least 500 messages; the test runs at exactly 500 (500 counted, targets, resent and completed). Open for Story 7.4: the dry run reads only each failure group's `Seen` set (the newest 1000 keys, `Settle.SEENMAX`), so past 1000 failures `affected` and `resend` fall below the incident's `Count` with nothing saying so.
- **Rejection, expiry, cancellation.** On a rejection or expiry no `Execute` is sent and nothing in the watched production changes. A cancellation sends no outcome; the incident stays as it is.
- **A fallback diagnosis, or a cause that isn't a data-format change,** gets no dry run and no request; Epic 5's fallback and no-fix notices stay.
- **Same-cause failures after the notice** never join an existing request's targets. If the incident is awaiting approval, fixing or resolved, they settle by the same rule and get their own dry run, request and notice; an Open incident only updates its count.
- **Approval before risk** in every configuration: the production's testing switch stays off, and each fix kind has a test that sends `Execute` without an approved row and expects nothing to happen.

## Technical Decisions

- **Footprint.** `src/ocutalon/cls/OcuTalon/Fix/**`, `Test/Fix/**`, `src/bridge/**` (except `src/bridge/cls/OcuTalon/BridgeExample/**`, Epic 13's), new files under `ci/mock/scenarios/A/**`, the merged Lane A areas `Watch/**`, `Checks/**`, `Tools/**` and `Live/Payload/Incident.cls`, and Lane A's tables (AD-33): `Data.Incident`, `Data.FailureGroup`, `Data.FixRun` and every `OcuTalon.Bridge.Data` class. `Install/**` is Epic 15's contended footprint: a new `Install/Step/<Area>.cls` is allowed (7.1 added `Install/Step/Fix.cls`, the Fix area's own step); editing any other existing `Install/**` file is not. The web incident and approval cards and the web and phone answer path are Epic 6's.
- **The answer path, as built (owner decision U-113).** `AnswersIn` checks the session and who may answer, then sends the answer synchronously to `AnswerOps`, whose job calls `OcuTalon.Bridge.Approval.Answer`. From there it is unchanged: `ApprovalHold` → `IncidentManager` → `FixExecutor` → `IncidentManager` → `Notify`. AD-11, AD-31 and AD-32 on this branch still describe the old path (Epic 6 amends them under U-120). Epic 7 builds from `Approval.Answer` onward; tests answer by calling it directly.
- **Fix kinds.** `OcuTalon.Fix.Kind` is the contract: `DryRun`, `Recheck` and `Execute` against fixed targets, a parameter schema, and `RESOURCES` in the form `resource:permission[,...]`, from which the service role's grants and the security overview's privilege list are generated. Permission checks use `$SYSTEM.Security.CheckUserPermission`, one letter per call (multi-letter checks were unreliable on build 154). No role ever holds `%Ens_MessageEditResend`.
- **Diagnosis validation.** The kind's parameter check (`Fix.Kind.Check`) runs last in `OcuTalon.Watch.Msg.DiagnosisPayload`'s validation, against the keys of the sample body in the evidence pack the request carried, read through `OcuTalon.Bridge.ReplyCheck` (begun by `Decide.Interpret`, cleared on every exit). With no pack every fix is refused. A reply that fails is `invalid` and takes Epic 5's fallback route.
- **Dependency rules.** Production components talk only through messages addressed by item name. `Fix.Msg.Execute` (`ApprovalRef`) and `Fix.Msg.FixResult` (`ApprovalRef`, `IncidentRef`, `Final`, `Total`, `Resent`, `Completed`, `FailedAgain`, `Skipped`, `Interrupted`, `Reason`) get no new properties. The dry-run ask from `IncidentManager` to `FixExecutor` is `Fix.Msg.DryRun` (`IncidentRef`, `FixKind`, `Parameters`), answered by `Fix.Msg.DryRunResult` (`IncidentRef`, `Targets`, `DryRun`, `Reason`). The bridge never references OcuTalon packages (a CI check), so the kind is a string on bridge rows; `ReplyCheck` is part of the bridge's shared API. In the domain layer `Watch` may reference `Fix.Kind` and `Checks` may call `Fix.Run.Sweep()`. Fix also references `Watch.Reader`, `FailurePoller.Scope`, `ItemNoun` and `Transitions`; the architecture doesn't list that yet (DW-328, with the owner), but the code is right, so leave it.
- **The dry run** reads the group's failed messages through `Watch.Reader` in the production's own namespace. Targets are only the messages in the incident's scope (the session whose `TraceRef` is their `SuperSession`, or `instance`). Its `DryRun` JSON has exactly the keys of `ApprovalRequest.DRYRUNKEYS`: `affected`, `resend`, `leftOut`, `field`, `before`, `after` and `itemNoun` (`{"one","other"}`).
- **Raising the request.** `IncidentManager` calls `Approval.Raise` once with kind `fix`, the `IncidentRef`, the targets and the exact change, the `DryRun`, the incident's `OwnerRef`, `ResultTarget` `IncidentManager` and the incident's trace session. `Raise` refuses inside an open transaction and starts the hold synchronously: OK means held, and a failed `Raise` leaves nothing. `IncidentManager` then appends the new `Ref` to `Incident.RequestRefs`. For kind `fix` the row's only contract column is `DryRun`; where the target ids and parameters live is the story's choice (appended bridge properties, since storage is append-only, or otherwise), but `FixExecutor` must load the kind, targets and change from the row alone.
- **Approval row states.** `pending` → `approved`, `rejected`, `expired` or `cancelled`; `approved` → `executing` → `done` or `failed`, or straight to `failed` when a run can't start. `StartExecution` needs an approved row whose `ExpiresAt` is ahead and fires no event. `FinishExecution(ref, done|failed|interrupted)` fires `approval.result`; interrupted leaves the row `failed`. Each change writes an `Approval` audit entry naming the approver for a run's start and end.
- **`IncidentManager`** is the only writer of `Incident` and `FailureGroup` and the only publisher of `incident` events, and moves the incident only by AD-15's transition table. A request counts as pending while `pending`, or while `approved` and the incident is still `awaiting_approval`. It refuses an `ApprovalOutcome` the row doesn't show. One fix runs at a time per incident: a `FixResult`'s own request never counts as waiting, and the earliest waiting request in `RequestRefs` order gets the next `Execute`. It publishes only after commit, each payload the full current view. `Live.Payload.Incident.FromRow` uses object access only, never SQL (`/state` has no SQL grant), opens each request by `Ref`, and takes each request's `Result` from the stored final counts.
- **Notifications.** Producers send catalog keys and slots, never text; the keys exist (`incident.withFix`, `incident.laterRequest` and `result.*` in `OcuTalon.Msg.Catalog.Watch`; answered statuses in `Catalog.Core`). Slots: UTC ISO 8601 times, integer counts, `itemNoun` as `{one, other}`, model-written slots as plain sentences without times. The first request's `ApprovalRef` and the dry-run slots (`field`, `before`, `after`, `resend`) ride on the kind-`incident` notice; kind `approval` is only for a later request. `answered` and `result` carry `ApprovalRef` and `IncidentRef`. `IncidentManager`, not `BridgeSink`, sends one notification per recipient from `Session.Recipients(ownerRef, incidentRef)`. The with-fix notice goes through Epic 5's notice delivery and sets `NoticedAt`.
- **`FixExecutor`.** An `Execute` carries only `ApprovalRef`. A refused `Execute` (pending, rejected, expired, cancelled, already executing or unknown) changes and sends nothing. Missing resources: a final `FixResult` with `Resent` 0 and a plain `Reason`, then `FinishExecution` `failed`. It resends from its one `New $NAMESPACE` method with `Ens.MessageHeader.ResendDuplicatedMessage(original, , target, newBody)`, building each body with the body class as resolved there, registers each new header id on the `FixRun` row, and waits up to 60 s per copy. A stopped target production returns `ErrProductionNotRunning`; that copy is `Skipped` with a plain reason. Measured on build 154: the copy runs in the target production, keeps the session and `SuperSession`, is marked `Resent` and is audited by IRIS; 500 copies resend in under a second.
- **A copy that fails again.** `IncidentManager` already keys failures `h<HeaderId>`; it must also recognise a registered copy's header id and count its failure against the fix, not a failure group.
- **Restarts.** `Install.Registry.CallAreas("Reconcile")` calls `Reconcile()` on every `Install.Step.<Name>` class. The Fix area's `Reconcile()` marks running `FixRun`s interrupted and closes their rows through `FinishExecution` `interrupted`. On every `Tick`, `Checks` calls `Fix.Run.Sweep()` and sends each final `FixResult` to `IncidentManager`: exactly one per run, never a second. Sweep's still-running branch is Story 30.5's.
- **Audit.** Only through `OcuTalon.Bridge.Audit.Record("Action", data)`, with exactly the members `irisUser`, `sessionRef`, `channel`, `action`, `target`, `result`, `counts` and `approvalRef` (`Record` refuses a missing or extra one). Tests read entries by `UTCTimeStamp` range, polling with a timeout, because the audit indexes lag up to 60 s.
- **Tests and the mock.** `%UnitTest` classes under `OcuTalon.Test.<Area>`. Lane A extends the mock only with scenario JSON under `ci/mock/scenarios/A/`; new mock behaviour is Lane B's. The mock logs every request to `/opt/ocutalon/mock-log/requests.jsonl`, the evidence for "no model request". For 50 failed orders without Break the feed, call `Partner.Send(count, dateFormat, traceRef, orderDate)` in OCUORDERS. Times convert only through `OcuTalon.Data.Time` (`Bridge.Time` in the bridge). Every persistent class commits its `Storage` block; stored properties are append-only.

## UX & Interaction Patterns

- **Voice.** Numbers first, then the cause, then the choice. "Nothing was changed." appears in every rejection, expiry and couldn't-start text. The phone and Telegram say "becomes", not arrows.
- **Texts the tests assert** (UJ-1 fixture):
  - Dry run: "Dry run: 50 orders affected. Example: order date 10/16/2026 becomes 2026-10-16. I'll resend 50 repaired copies; the originals stay unchanged. Nothing has changed yet."
  - Later request: "3 more orders failed since 14:20 ET, with the same cause. I can repair and resend all 3. Approve?", then its own dry run, then "Details and trace: on your OcuTalon page."
  - Results: "All 50 orders went through.", the failed-again and skipped partials, and "Nothing was resent: {reason}. Nothing was changed." (fixture reason "OcuTalon isn't allowed to resend messages in that production").
  - Restart: "The resend stopped when OcuTalon restarted: 30 of 50 orders went through. The other 20 need a new approval."
  - The catalog also has count-of-one forms.
- **On the page** (Epic 6's): each request card shows its own answered status ("Approved from {channel} at {time}") and result band, then "Recorded in the IRIS audit log." The demo guide's finish needs an approved fix and a resolved incident.
