# Epic 11 Context: Release 1 ships: the demo path end to end, upgrade in place and a scripted release

## Goal

Epic 11 is release 1's merge point. With every floor epic (0 to 10) merged, it turns the whole web demo path (UJ-1 without Telegram) on end to end in the REL-2 Playwright test, on real components. It also builds the release machinery in `release/`: an upgrade-in-place and restart harness that shows every record survives, a clean-machine rehearsal (install, first start, then N timed demo-path runs checked against every bound) proved on throwaways, draft notes and a release checklist, and one scripted sequence that cuts a candidate, runs every gate and stops for the author's word before any outward step. The first release is 1.0.0. 0.1.0 and 0.1.1 are not cut. The real 1.0.0 check and cut (the real-key pass, the timed rehearsal on a real droplet and the Telegram pass) are Epic 38's, run through this epic's sequence.

## Requirements & Constraints

- **Demo path (REL-2).** Every UJ-1 step spec under `web/e2e/demo-path/` except Telegram's runs in order and passes on the CI mock: sign-in, watch (Act strip, Orders check row), reminder, Break the feed to one incident awaiting approval, Approve on the simulated phone to "All 50 orders went through.", and the trace. After the browser steps, the IRIS audit log (polled with a timeout) must hold the approval's answered entry and the resend's action entry, with no key, token, password or Telegram identity in either. Against the real model, tests assert only that a decision with reasons and a trace link appears, never which outcome. The online-demo run lives in `web/e2e-online/`. A full CI run must stay within 35 minutes.
- **Turn-ons (Story 11.9).** Turn on every check left off by a "turns on when … merges" clause in Epics 0 to 10, except checks such a clause leaves for Epic 30 or 31. Fix the listed CI flakes so a candidate needs no reruns.
- **Upgrade and restart (FR-60, NFR-16, NFR-17).** These records survive an in-place upgrade and a container restart: conversations (the next turn carries the history), reminders (fire late if they fell due), pending approvals (original expiry, still approvable), watches, a demo-mode-off setting and, from the release after 1.0.0, pairings (Story 12.7 extends the harness). 1.0.0 has no previous release, so the harness runs from a pre-release integration-branch build to prove itself; it is a required gate from the release after 1.0.0.
- **Rehearsal install (Story 11.3; REL-6, FR-55).** Reach the clean host and the driver host over SSH with addresses and keys from the author's configuration outside the repository; copy the candidate as a `git bundle` and clone it (no other outbound access needed); run `install.sh` with the key in the host's `.env`; wait for ready, read the printed address and sign-in details, and record the first start's duration, install included. A failed step fails the rehearsal, names the step and blocks the release.
- **Rehearsal timing (Story 11.11; NFR-3, NFR-7 to NFR-10, P30, UX-DR102).** The runner drives the REL-2 specs from the driver host against the clean machine N times (20 for a real rehearsal), using Run again and the replay rule between runs. It splits each run's Break the feed to notice time, from production message timestamps, into pick-up (15 s), settle end (30 s after the first failure), diagnosis (20 s) and delivery (5 s), and checks: NFR-7's 60 s in at least 19 of 20 runs; the median against about 35 s; step 1's decision time (10 s, 19 of 20); the approval result's 2 s; each reminder firing within 10 s; the largest model request under 100,000 input tokens; the first reply's time; when the reminder lands relative to "All 50 orders went through."; the tell-now notice's 5 s in 19 of 20. A failed run or missed bound fails the rehearsal and names the run, the step and the bound. Twenty runs exceed one 10-minute call, so runs must be splittable across calls.
- **Dry runs only in this build.** There is no clean host and never a real key: every rehearsal test runs on throwaways with the CI mock, and the report and record mark such a run "dry run", never a pass. 11.11's tests include a planted missed bound. For 1.0.0 the real run uses one clean Linux droplet driven from the Contest Planner's Mac, with no macOS run (Story 38.2).
- **Notes and checklist (REL-8, CON-2, CON-5).** Notes are plain language, grouped by area, claim only what ships; class names and error codes only in a developer section; for 1.0.0 they cover every merged story. The checklist verifies the verbatim OpenClaw non-affiliation note in the README and About text, no "OpenClaw" in the product name, every bundled package, font and icon set keeps its licence notice, the public-text check passes and no IRIS reference source is tracked, the author's review of `_bmad-output/` before going public, and README links resolve on the public page.
- **Release sequence (REL-1, REL-3, REL-7, REL-11).**
  - For the first release it refuses any version except 1.0.0, and any version already tagged. The candidate branch is `release/<version>-rc<n>` and never changes after the cut; a failed gate means a fix on the integration branch and a new `rc<n+1>`.
  - Gates: full CI, the release-candidate evaluation with the demo gate, the upgrade harness, the rehearsal, the checklist, and the hands-on pass (for 1.0.0, Stories 38.1 and 38.3). REL-5's is the only override accepted. It refuses a candidate with an enabled item answering "not implemented" (`Parameter STUB = 1`).
  - The author's hands-on time is at most 15 minutes. The record lives at `release/records/<version>/rc<n>.md` on the integration branch.
  - The IPM artifact bundles the built web page in `src/ocutalon/csp/`; the record names the artifact for Story 15.3. The registry publish stays the author's action.
- **Secrets and the image (NFR-11, CON-1, CON-5).** No step prints an environment or configuration value: `docker compose config` only with `--quiet`, `docker inspect` only with `--format`. No step pushes an image or signs in to a registry. Records describe machines only by OS, CPU architecture and memory, never host name or address.

## Technical Decisions

- **Storage is append-only (AD-5).** Never rename, retype or remove a stored property. The storage diff runs against the highest earlier `v*` tag. Every private global resolves to the private database. Rows are the truth for `ApprovalHold` and `ReminderTimer`; `Reconcile` re-arms missing waiters from them.
- **Upgrade path (AD-23).** On start, the after-start script deletes the ready marker, runs the version-gated IPM upgrade, then the installer steps in fixed order: bridge installer; `Public` (readiness stays cleared); roles and users; web applications; `Demo`; Config Store entries; audit events; Telegram items; `Production`; `Reconcile`; `SetReady` last; the ready marker. Demo mode switches only through `OcuTalon.Core.Admin.SetDemoMode`. Release steps check the version inside the built image (a cached build context can bake stale sources). `src/module.xml` holds the version.
- **CI mock (AD-22).** Scenarios are JSON under `ci/mock/scenarios/<lane>/`, selected by: a `[[mock:<name>]]` marker; then a guide prompt (`B/` only), optionally narrowed with `match: {prompt, mockkey}`; then the agent's `MOCKKEY` default script (`triage`, `diagnosis`, `chat`). Lane A adds only files under `A/`; new mock behaviour is Lane B's.
- **Incident timing (AD-15).** `FailurePoller` polls every 3 s; the settle rule is 10 s of quiet or 30 s after the first failure; the notice sets `NoticedAt` (UTC) and before it only `watch.progress` events (`noticed`, `settling`, `diagnosing`) go out. These are the hooks 11.11's splits measure against.
- **Rehearsal script interface (Story 11.3, consumed by 11.11 and 11.5).**
  - `release/rehearse.sh` with phases `plan`, `install`, `report`, `down`, and `run` (install, report, always down), each its own process, keyed by `OCUTALON_RUN_TAG`; options `--version`, `--rc`, `--candidate`, `--record`, `--dry-run`.
  - Shared `release/lib-release.sh`: `release_config_read` (one `release.conf` outside the repo, `REHEARSAL_`-prefixed keys; a `DEMO_` prefix can join it for 11.5's hook), `host_run <clean|driver> <cmd>` (every remote action; strict host keys, BatchMode), `record_path`, and `record_write <file> <section>` (replaces only its own `## ` section; Story 11.2's harness writes through it too).
  - Failure lines read `FAIL run <run> step <step> bound <bound>: <detail>` (11.3 uses run `install`). Results: `fail` if any step failed; else `dry run` in a dry run; else `not run` while any row is `not run`; else `pass`. Exits: 0 real pass only; 1 fail or not run; 2 refusal; 3 dry run; 75 lane lock busy.
  - The record section `## Clean-machine rehearsal` carries `Result:` and `Mode:` lines and a step table; its `demo path runs` row is `not run` until 11.11, so a real run cannot pass before 11.11. 11.11 adds a `runs` phase between `install` and `report` and the bounds rows.
  - 11.5's gate runs `OCUTALON_RUN_TAG=<t> bash release/rehearse.sh run --version <v> --rc <n>` (`--dry-run` for its rehearsal candidate) and passes only on exit 0 with `Result: pass`. The rehearsal is not a CI unit.
- **Release-candidate evaluation.** `bash eval/run.sh --release-candidate` writes `eval/release-candidate.json` and `.md`; `--override "<reason>"` records the author's override. The notes take their evaluation summary from these files.
- **Demo-host hook (AD-25).** Only over SSH, with address and key from the author's configuration outside the repository. It copies a `git bundle` of tag `v<version>` and runs `ocutalon-demo update <version>` (prints `{"result":"updated",...}` while access is restricted, `{"result":"scheduled","at":...}` after launch), then reads `ocutalon-demo status` (running and golden versions, last and next reset, `pendingVersion`, `access`). Tested against a throwaway stand-in host. With no demo host configured, the notes say the online demo wasn't updated.
- **Lanes (AD-29).** `release/` is Lane A's. Epic 11 is the AD-29 exception: it may change either lane's files to make the demo path pass, serialized against overlapping epics. `ci.yml` is Lane B's, `lane-a.yml` Lane A's. After a release, `main` merges back into the integration branch. Step epics merge only once `release/1.0.0-rc1` exists.
- **Merging to `main`.** Only with the `ci.yml` and `lane-a.yml` checks green. While the repository is private (branch-protection queries answer HTTP 403), the sequence checks every job itself and records that it did.
