## Intent

**Problem:** A production developer cannot reach OcuTalon's status and history from their own MCP client; there is no `OcuTalon.Mcp.Service`, no `/mcp/ocutalon` application, no `OcuTalon_MCPServer` resource and no `OcuTalonMCPClient` role (FR-51, step 7).

**Approach:** Add `OcuTalon.Mcp.Service` (a `%AI.MCP.Service` subclass guarded by `OcuTalon_MCPServer`) whose one toolset offers two read-only tools, `check_status` and `recent_activity`, that run as the calling IRIS user and read only that user's OcuTalon session through the ownership API; the Mcp area's installer step creates the resource, the password-only application and the role (none of them on the online demo); every served call is audited; the security overview lists the tools and the role. **Build scope is split (gate item G7):** Task 0 measured that `iris-mcp-server` 2.0.0 cannot yet list or call any `%AI.MCP.Service` tool on build 154, so the gateway configuration AC and the successful end-to-end call through an MCP client move to a new Story 28.5.

## Boundaries & Constraints

**Always:**
- **R-28.3-1 (BINDING, Planner condition 1): MCP clients only ever get read-only tools, under IRIS authentication; offering a state-changing tool is impossible by construction.** (a) The service's specification is the compile-time constant `OcuTalon.Mcp.ServiceTools`, whose tools are methods of `OcuTalon.Mcp.ServiceRead` only. (b) `Service.ReadOnlyProblem()` checks every tool of the specification through the gate's own readers (`Bridge.Adapter.StepBuffer.ToolParameter`, `Bridge.Policy.Gate.HookFor`): classification exactly `safe`, `READONLY` exactly 1, no `Classify`/`Hold` hook, provider in package `OcuTalon.Mcp.`; `OnAuthenticate` refuses every request (discovery and calls) while it is not "". (c) The role holds R and never W on any database, so any write in a served call fails `<PROTECT>` (measured). (d) The service never begins a bridge context, so `Tools.CommandCall` answers NOSESSION and submits nothing (measured). (e) Tests prove (b) for the shipped specification and walk the full tool inventory.
- **R-28.3-2: owners never mix (AD-4).** A served tool takes its owner only from the calling IRIS user (`$Username`), by a read that never creates a session row, and reads only through `OcuTalon.Data.Ownership` and the row readers the chat tool already uses on rows it gave (`FailureGroup.OfIncident`, `FixRun.OfRequest`); no argument names a session or a user.
- **R-28.3-3: off on the online demo.** Detected by `+##class(OcuTalon.Data.Public.Settings).Get("onlineDemo") = 1` (the installer's seam, in the public database, readable by the role: measured). There the Mcp step creates no application, resource or role (and deletes the application and resource if present), `Grants()` declares none, `OnAuthenticate` refuses with P1, and each tool answers P1 and reads nothing.
- Every served call writes exactly one IRIS audit entry through `OcuTalon.Bridge.Audit` (type `MCP`, change `served`, server `ocutalon`, the tool, one outcome word, `irisUser` the caller, `sessionRef`, channel `mcp`); never an argument, a result or any text. If the entry cannot be written the call returns P4 and no data (fail closed).
- Tool answers are built in code (trusted output, as the chat tools'); they never log a warning (the role cannot write the event log) and return through `Tools.Result.Return`.
- The chat path is unchanged: `Tools.RecentActivity`'s description, answers and classification stay byte-identical.

**Never:**
- No Lane B file (U-177, AD-29): not `Install/Step/Web.cls` (Lane B's web step), `Test/Web/**`, `Data/Session.cls`, `Data/Ownership.cls`, `Core/**`, `Msg/Enum.cls`, `Bridge/Msg/Enum.cls` channel list, `ci/units.sh`, `README.md`.
- No change to `OcuTalonUser`, `OcuTalonServiceRole` or any other existing role; no grant to the demo, read-only, trace or public accounts; no `%All`, `%Development`, `%Admin_*`, W on any database or SQL privilege for `OcuTalonMCPClient`.
- No new container, compose service, dependency or `iris-mcp-server` configuration in this story (Story 28.5).
- No model-facing change for OcuTalon's own agents; no new user-facing text ships unless the Planner accepted it (PUBLIC TEXT below).
