## Intent

**Problem:** An admin can connect a mailbox only with a stored password. Gmail and Microsoft 365 want OAuth2, and nothing registers an IRIS OAuth2 client, runs the consent, or keeps the client secret and tokens out of OcuTalon's own stores. IRIS's redirection endpoint `/csp/sys/oauth2` is disabled on the image (measured in plan), so a consent cannot even return today.

**Approach:** Settings > Channels > Email gains a sign-in method (Password, Google, Microsoft 365) with Client ID, a write-only Client secret, the redirect address to register, and "Sign in with {provider}". The secret travels REST -> `SecretHandoff` -> `SettingsOps`, which registers IRIS's OAuth2 client `OcuTalonMail` through ONE new class that switches to `%SYS` (`OcuTalon.Channel.Email.OAuth`, added to AD-3's list). A new admin route starts the sign-in (IRIS's own authorization-code URL, opened in a new tab) and checks it afterwards; the tokens stay in IRIS's OAuth2 client. The CI mock gains a fake OAuth2 authorization server; no real provider is ever reached. Token use by `EmailIn`/`EmailOut`, refresh, the revoked-grant reason and the README move to the proposed sibling Story 21.8 (Design Notes, "Proposed split").

## Boundaries & Constraints

**Always:** Lane B files only (`Core/**`, `Web/**`, `Channel/**`, `Msg/Command/**`, `web/`, `ci/mock/**`, Lane B tests); contended files get the small placed edits of Design Notes "Contended files". The client secret never enters a command, message, log, trace, global, audit entry, GET or test output: the command carries only `secret://handoff/<name>`, and its one home is `OAuth2.Client.ClientSecret`. Tokens live only in IRIS's `OAuth2.AccessToken` (application `OcuTalonMail`, session `OcuTalonMail`); OcuTalon never reads or copies a token value in this story. `SettingsOps` (its production job) is the only caller of the `%SYS` class; REST writes nothing and reads no `%SYS` object (AD-1, AD-19). Exactly one method of `OcuTalon.Channel.Email.OAuth` switches namespace (`New $NAMESPACE`). Provider endpoints are fixed `https://` constants called over `OcuTalonClient` (VerifyPeer on) with the host-name check (V7); no discovery call, no accept-any-certificate option. Any value holding `@{` is refused and nothing changes. Online demo: no email settings show, both routes answer 409 (P2), `SettingsOps` and the `%SYS` class refuse, `/csp/sys/oauth2` is never enabled. ASCII-only source (Rule 14); comments state the contract.

**Never:** a Lane A file (`Mcp/**`, `Tools/Email*`, `Bridge/**`, `Install/**`, `Fix/**`, `Digest/**`, `src/bridge/**`, Lane A tests); the adapters' OAuth2 settings rows, an OAuth2 callback handler class, XOAUTH2 in the POP3 or SMTP stubs, refresh or revoke handling, a poll reason for a revoked grant, or README text (all Story 21.8); a revoke call to a provider; OAuth2 discovery; IRIS Workflow requests (the default `Ens.Util.OAuth2.Handler` raises them: nothing in this story calls it); modifying or deleting an `OAuth2.ServerDefinition`, `OAuth2.Client` or web-application setting that OcuTalon did not create or change; a real provider, client ID, secret, token or account in any test, fixture or CI run; a new role, grant, resource, table, `ci/units.sh` unit or group; `Ens.Director.EnableConfigItem` or a save of the production definition.
