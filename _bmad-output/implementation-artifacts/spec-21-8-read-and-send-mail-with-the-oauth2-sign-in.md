## Intent

**Problem:** Story 21.3 registers IRIS's OAuth2 client `OcuTalonMail` and signs the mailbox in, but `EmailIn` and `EmailOut` still log in with the stored credential, which in provider mode has no password: every poll fails with "The mail server refused the user name or password." (DW-1179) and every send is refused. Nothing refreshes an expired token, a revoked grant has no plain reason, the README says nothing about Google or Microsoft 365, and the privileges that registering needs were measured only under `_Ensemble` holding `%All` (DW-1180).

**Approach:** With a provider saved, `SettingsOps` writes two more System Default Settings rows on both mail items: `OAuth2ApplicationName` `OcuTalonMail` and `OAuth2CallBackHandler` `OcuTalon.Channel.Email.Token`, a new subclass of IRIS's `Ens.Util.OAuth2.Handler` that names the session `OcuTalonMail`, refuses on the online demo and never raises a Workflow request. The adapters' existing OAuth2 lines then fetch the token through IRIS's `%SYS.OAuth2.AccessToken.IsAuthorized` (IRIS refreshes an expired token itself) and log in with XOAUTH2; a token that cannot be had, or an XOAUTH2 login the server refuses, gives one new plain reason. The CI mock gains refresh, revoke and short expiry on its fake OAuth2 server and XOAUTH2 on its POP3 and SMTP stubs. A live test lists every privilege registering needs, each with a check that registering is refused without it. The guide explains the Google and Microsoft set-up.

## Boundaries & Constraints

**Always:** Lane B files (`Channel/**`, `Core/**`, `ci/mock/**`, Lane B tests), plus the guide (README.md, or GUIDE.md once Story 0.30 is in; footprint extension). The access token exists only in IRIS's `OAuth2.AccessToken` and, during one poll or send, in the adapter job's memory on its way to `%Net.POP3`/`%Net.SMTP`. It never goes into a message, a log line, the trace, a status mark, an audit entry, a global, a GET, the mock's state or test output. `SettingsOps` is the only writer of the rows. Password mode works exactly as before (USER/PASS, AUTH PLAIN/LOGIN, the 21.2/21.6 sentences). The production job still runs as `_Ensemble`. Online demo: no rows are written, the handler refuses, and both items stay disabled. ASCII-only source; comments state the contract (Rule 14). Every 21.3 guard stays green: `Channel.Email.OAuth` still has `SettingsOps` as its one caller, and `Sys` still does only what S1 lists.

**Never:** a Lane A file; a new namespace-switching method; a call to `Channel.Email.OAuth` from any class other than `SettingsOps`; an `OAuth2Scope`, `OAuth2SessionId` or `OAuth2AuthProperties` row; an IRIS Workflow request (`EnsLib.Background.Workflow.OAuth2Request`); a revoke call to a provider; a grant, role or resource added to any OcuTalon role or install path (the DW-1180 fixture role and user are test-only, on throwaways, removed after); a real provider, client, token or mailbox in any test or CI run; a new route, command, table, product key, `ci/units.sh` unit or group; any text that says or implies least privilege (DW-1180).

## Design Notes

**Governing ADs (Rule 6):** AD-1 (no new command or route; `SettingsOps` is the only writer of the item rows), AD-3 (no new switching class: IRIS's own `GetAccessToken` switches to `%SYS` inside the call, just as 21.3's `Start` reaches `%SYS.OAuth2.Authorization`; `Channel.Email.OAuth` keeps its one caller and its S1 scope), AD-10 (no new tool path; the tool send keeps its AD-10 rules), AD-14 (email channel, `emailPoll` contract, the Delivery rows), AD-17 (no new audit entry: the rows follow the `email.signIn` change already audited), AD-19 (token homes; S1), AD-22 (mock; S3), AD-24 (no grant, the production as `_Ensemble`; S2), AD-25 (online demo), AD-29/AD-33 (Lane B). No AC contradicts an AD Rule. AD-19's 21.3 bullet says "OcuTalon reads only whether the row holds an access token ..., never a value, and never refreshes or revokes" and in the same bullet "Token use by the adapters, refresh and revocation are Story 21.8's". This story reads that sentence as describing 21.3's registration and state code (`Channel.Email.OAuth`), which stays as it is, and adds the adapters' token use as S1 (veto V5).

**Already met (21.3, evidence):** epics AC 1's consent half ("the provider's consent page opens in a new tab, and after consent IRIS's OAuth2 client holds the tokens"): `Test.Channel.EmailLive` `TestOAuthSaveSignInAndRemove` (the full code flow through IRIS's `OAuth2.Response` and the mock; the token row holds `mock-at-`/`mock-rt-` tokens with no error) and `web/e2e/settings/email.spec.ts` E6 (new tab, landing, signed-in state), both green on this branch. 21.8 adds only the token-use half.

**Ledger (Rule 17):** DW-1179 addressed: matrix rows "Provider saved" and "Not signed in yet", the `SettingsOps` rows task, the DW-1179 AC. DW-1180 addressed: Task 0 (e), the `EmailOAuthPrivileges` task, the DW-1180 AC, the least-privilege grep AC, veto V4. **Declined DW-1185: already resolved by Story 21.3** (its rework 1 made `SysAuditMasks` look for the test's own entry after a time mark, with a bounded 30 s poll; the mutation lines are in 21.3's Verification; `ledger.sh` should show it `resolved-by:21-3-...`).

**Decided in-stage:** (1) The session is named by the handler (`GetDefaultSessionIdForRunningHostItem`), because `OAuth2SessionId` is not in IRIS's SETTINGS, so a row could never set it (read from `Ens/Util/OAuth2/Settings.cls`). (2) No `OAuth2Scope` row: the scope is fixed at consent by 21.3's constants, and `IsAuthorized` with a scope refuses a token whose granted scope lacks one of them. Microsoft's token response leaves out `offline_access` (inference from Microsoft's documentation; the mock copies it). (3) No `OAuth2AuthProperties` row: it is used only to build an authorization URL, which this handler never does. (4) Every `OnNotAuthorizedGrant*` is overridden, so no row value can make the handler fetch a token another way or raise a Workflow request. (5) In OAuth2 mode a refused login means the sign-in is no longer accepted, so it gives the same reason as a token that cannot be had; this covers a revoked grant whose access token has not expired yet. (6) GET `signedIn` is derived as false after a poll failed on the sign-in, so Settings never says "Signed in with Google." while polls fail; the button to sign in again is already there (N4).
