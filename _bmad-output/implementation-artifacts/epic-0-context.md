# Epic 0 Context: OcuTalon installs, starts and lets you sign in

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Epic 0 is the walking skeleton. A judge loads and retags the build 154 image, runs `docker compose up`, and gets OcuTalon in its own OCUTALON namespace, installed and upgraded by its one IPM package at every start, with an empty, branded page behind sign-in and, in demo mode, the Orders production running in its own OCUORDERS namespace. Its real job is to unblock two parallel build lanes: it creates every cross-lane release-1 contract with its final name, type and storage, stubs every release-1 production item inside lane-owned regions, and sets up CI with the model mock and a demo-path test, so each lane starts its first story without editing the other's files. One runner, time-boxed to three days from the build start; it ends October 23 at the latest.

- Story 0.4: The cross-lane message and data contracts (done)

- Story 0.8: The demo-path test signs in and loads the page (done)
- Story 0.9: The message catalog and its one renderer (done)
- Story 0.10: The Orders demo production runs in OCUORDERS (done)
- Story 0.11: The CI model mock answers every scenario the stories need (next, and Epic 0's last; Lane B). It adds the `mock` service to 0.7's `ci/compose.ci.yml`, replaces the `web` job's "Mock tests" step, keys on 0.6's `MOCKKEY`s, `Tools.Names` and `OCUTALON-COMPACTION-V1`, is reached through AD-19's endpoint overrides, keeps the no-key start, fixes the scenario format under `ci/mock/scenarios/<A|B>/`, and stays inside REL-4's margin and the CON-3 check (see Cross-Story Dependencies).

## Requirements & Constraints

- **Install:** after a load and retag, a plain `docker compose up` gives a working install. The first start creates OCUTALON with Interoperability and its own databases. Later starts reapply the same configuration with no errors and no data loss.
- **Demo mode:** on by default for the `docker compose up` install, off for an IPM install into an existing instance; an admin can switch it (4.1). With it on, the Orders production is installed and running in its own namespace, OCUORDERS. With it off, none of the demo features exist and nothing else changes. Nothing on the demo path is canned: the orders fail as real errors in a real transform, and mocks exist only in CI's configuration.
- **Roles and sign-in:** the install creates the user, admin and trace roles and the README account (`ocutalon`/`ocutalon`, non-expiring, no forced change). No page or API answers without a session, except the login page and `/ocutalon/public/status`.
- **Secrets:** model keys and bot tokens come only from environment variables (`.env`, git-ignored; `.env.example` lists the names). No key appears in logs, traces, audit entries or the repository.
- **Image and registry:** the AI Hub image, or any image built on it, is never pushed and never enters a CI cache or artifact; CI fails on any `docker push` or registry sign-in. The judges' compose file has no mock service.
- **Tracked files:** no tracked or new file holds a local machine path or a key-like string; a CI check scans the whole tree, the planning, bookkeeping and `eval/` folders included.
- **CI:** a full run takes at most 30 minutes. IRIS tests run on the self-hosted runner, everything else on paid hosted runners; fork pull requests never reach the IRIS runner. The model mock serves the same Anthropic provider path the product ships, so refusal and sampling-parameter tests cover the real path. The demo-path test runs on every pull request and push to `main`, and a red demo path turns the `ci` run red. `main` moves only through a release pull request.
- **Platform:** the same Dockerfile works unchanged on the non-Health build 154 image through the `IRIS_IMAGE` build argument.
- **Epic 0 is done when:** a clean first start reaches ready and a second upgrades in place; every release-1 item runs as a stub (`TelegramIn`, `TelegramOut`, `EvalIn` disabled); every class compiles with its storage block committed; CI runs with the mock and the boundary, storage, `DEFAULTGLOBAL` and public-text checks; the demo-path test passes; and neither lane needs the other's files for its first story. A first start over about 12 minutes goes to the author.

## Technical Decisions

### Governing rules (by AD id)

- **AD-2 (one package, separable bridge):** one IPM package, `ocutalon`, listing the bridge (`src/bridge/`) before `src/ocutalon/`; the bridge also loads alone into an Interoperability namespace (`Bridge.Installer`). CI fails if a bridge class references another `OcuTalon` package (`bridge-refs`), or if a class outside `OcuTalon.Bridge`, `.BridgeExample`, `.Agent`, `.Tools`, `.Docs`, `.Memory`, `.Mcp`, `.Install` and `.Test` references `%AI` or `EnsLib.AI` (`ai-allowlist`). `OwnerRef` is exactly a `SessionRef`, `instance` or `eval`.
- **AD-3 (namespaces and databases):**
  - OCUTALON has code, data, private and public (`OCUTALON_PUBLIC`, public Read) databases. The public database holds only `OcuTalon.Web.Public` (`Login`, `Status`, `Shell`, `SignInAssets`, `ApiBase`), `OcuTalon.Data.Public` and `^OcuTalonPublic`, mapped into OCUTALON and, with demo mode on, OCUORDERS.
  - Those packages may reference only `%CSP` (including `%CSP.REST`), dynamic objects, `$SYSTEM.License`, `$SYSTEM.Status`, `$SYSTEM.Encryption` (only in a compile-time generator), system datatype classes as types, and each other; never the catalog (`Test.Web.Status`; DW-20, escalated).
  - Global mappings put `OcuTalonP.*` and `OcuTalonBP.*` (with the dot, so `^OcuTalonPublic` stays public), `^AI.Agent.Session*` and `^IRIS.IF.*` in the private database, before any class compiles.
  - Business processes store in `Ens.BusinessProcess`'s own extent (no `DEFAULTGLOBAL`) and keep no private text in their properties. `OcuTalon.Production` is not autostart on Docker.
  - **OCUORDERS (demo mode):** `OcuTalon.Demo.Orders.Production` runs there with its own code and data databases, reaching its classes through a package mapping of `OcuTalon.Demo.Orders`. `Install.Step.Demo` creates it with no Foundation, owns only an OCUORDERS on its own directories, and with demo mode off removes it whole (0.10 below).
  - **Namespace switching:** only `OcuTalon.Install.*`, `OcuTalon.Bridge.Installer` and `Install.Step.Demo` switch namespace in Epic 0's product code, in one method per target namespace with `New $NAMESPACE` (the Demo step's `System` to `%SYS` and `Orders` to OCUORDERS). Later: `Watch.Reader`, `Fix.Executor`, `Demo.PartnerTrigger`. Test classes switch to `%SYS` for fixtures (DW-7). Nothing may depend on the non-Health image's missing Foundation production or its `/csp/<ns>` default application.
- **AD-5 (durable state):** all state lives on the durable volume: durable `%SYS`, OCUTALON's data and private databases and OCUORDERS's data database (OCUORDERS has no private database). An install replaces only code. Storage is append-only, with the compiler-generated `Storage` block committed and never hand-edited. The production class holds structure only; values go in System Default Settings, bridge tables or `Data.Setting`.
- **AD-19 (configuration homes):** model keys and bot tokens are environment-only. The endpoint overrides `OCUTALON_MODEL_BASE_URL` (ending in `/v1/`), `OCUTALON_EXTRA_CA_FILE` and `OCUTALON_TELEGRAM_API_BASE` are set only by the CI override and the online demo; the installer builds the provider configuration from them. Every value the installer writes is `structural` (rewritten every start) or `seed` (written only when absent; `SettingsOps` owns it after). `Data.Public.Settings` is the only reader and writer of `^OcuTalonPublic` (a fixed key set, the online-demo flag among them). Product values no bridge class reads (demo mode, digest time, thresholds, the idle cap) live in `Data.Setting`, read through `Setting.Get` with a 60-second cache. Demo mode is the seed key `demo.mode` ("1" or "0"), which the Demo step seeds to "1" where `/opt/ocutalon/version` exists (OcuTalon's own image) and to "0" otherwise.
- **AD-23 (image and installer):**
  - **Image:** one Dockerfile, `FROM ocutalon-iris-base:2026.3.0AI.154.0`. Every compose file sets its own `name:`; the judges' one publishes only `${OCUTALON_WEB_PORT:-52773}` and names no file of `ci/`.
  - **Start:** `docker/merge.cpf` (Lane A) creates OCUTALON's databases, namespace and mappings (never OCUORDERS's) every start. The after-start script re-merges, installs IPM 0.10.10, loads the package version-gated (`OCUTALON_DEV=1` reloads every time), runs the registry's steps and writes the ready marker atomically (none on failure), logging `STEP <name> OK|FAILED` and `RESULT OK <version>` to `/durable/ocutalon-after-start.log`. `start_period` stays at least 10 minutes. Static web files go in the durable `csp/ocutalon-web/`, never `csp/ocutalon/`.
  - **Step registry:** every step extends `OcuTalon.Install.Step` (`Run()`, no arguments); `OcuTalon.Install.Registry` runs the fixed order, and a step class outside it only declares. Areas declare `Grants()` (`{"role","resource","permission"}`; empty `resource` declares the role alone), `Reconcile()`, `Tasks()` (`{"name","taskClass","description","task":{...},"settings":{...}}`, created once) and `Purge(daysToKeep)`. Role and task names start with `OcuTalon`. An IPM install calls `Registry.Run("ipm")`, with demo mode off.
- **AD-13 (web applications, sign-in and the envelope):**
  - **One sign-in group** (`GroupById` `OcuTalon`, password): `/ocutalon` (dispatch `Web.Public.Shell`), `/ocutalon/api` (`Web.Api`, `/v1`, sharing `/ocutalon`'s CSP session) and the trace applications. `OcuTalonUser` holds no database resources; the applications grant them as application roles. `/ocutalon/public` (unauthenticated) serves only `GET /status`: `{ready, nextReset, busy, lastReset, lastResetKind}`, `null` when unset.
  - **Before and after sign-in:** without a session, `ApiBase` answers 401 `signed_out`; a signed-in user without the user role gets 403 `no_role`. The login page (`%CSP.Login`) loads nothing from an authenticated path.
  - **SQL privilege:** `OcuTalonUser` holds no SQL grant, so the API's queries over the user's own rows use `%Prepare(text, 0)` with fixed texts, ownership enforced in the query; the `unchecked-prepare` rule allows that only in `Session.ForUser` and `Live.Event.Since` (DW-17, DW-24). Until 2.2, `/state` and `/events` find the session by user name (DW-15).
  - **The browser envelope:** every state-changing call needs `Content-Type: application/json`, `X-OcuTalon-Request: 1` and a matching `Origin`, or it gets a 403. GET, HEAD and OPTIONS are exempt.
- **AD-24 (roles and trace applications):** the roles are `OcuTalonUser`, `OcuTalonAdmin` and `OcuTalonTraceViewer`. The trace role holds `%Ens_Portal`, `%Ens_MessageTrace`, `%Ens_MessageHeader` and `%Ens_MessageContent` (Use), read on both namespaces' data and code databases (never the private ones) and SQL `SELECT` on `Ens.MessageHeader` in both; its OCUORDERS grants exist only with demo mode on. The trace applications `/ocutalon/trace/ocutalon/` and `/ocutalon/trace/ocuorders/` (the latter only with demo mode on) come from `Install.Step.Web.TraceApp`: sign-in group, exactly S7's seven `PermittedClasses`, no application roles. No OcuTalon role holds `%All`, `%Development`, `%Ens_MessageEditResend`, `%Ens_MessageDiscard`, `%Ens_ProductionRun` or `%Ens_ProductionConfig`. No `OcuTalon.Data` or `OcuTalon.Bridge.Data` class extends a message base.
- **AD-12 (live events):** rows are written only through `Live.Publish`, after the publisher's own commit, never inside a transaction; each event-table type has exactly one publisher; `Seq` comes from a per-stream counter the purge never deletes. A payload is the full current public view of one entity, keyed by `Ref`, never a delta: a `%JSON.Adaptor` class `OcuTalon.Live.Payload.<Type>` of the publisher's lane (keys camelCase). Trace targets are `TraceHeaderId` and `TraceNamespace`. Polling is the release-1 contract. Status conditions are a closed catalog: `allowance`, `dailyCap`, `noModelKey`, `heartbeatStalled`, `telegramPaused`, `resetSoon`.
- **Contract semantics fixed in Epic 0:**
  - **`Commands.Submit` (AD-1):** the only way to submit a command. It validates the caller's origin, overwrites the payload's `Origin` with it (`tool` while a bridge context is active), and sends to `CommandsIn`; role checks stay with the admin-checked endpoints and `CommandsIn`. Origins: `web_user`, `web_admin`, `telegram`, `tool`, `timer`, `system`.
  - **`Reply.Busy` (AD-6):** set when `Decide` refused a `turn` after a 2-second lock wait; the `Reply` carries no text and no decision (`Reply.NewBusy()`), and busy is never an error status.
  - **`Decision` (AD-20):** unique on (`ItemId`, `Kind`).
  - **Time (AD-18):** `OcuTalon.Data.Time` is the only converter outside the bridge, `OcuTalon.Bridge.Time` (1.4) the only one inside it. Times are stored and sent as UTC; message text uses the instance's zone (the container's `TZ`, inherited by every production job), the page the browser's.
  - **Audit (AD-17):** `OcuTalon.Bridge.Audit` is the only audit writer; OcuTalon never changes instance-wide auditing. Tests poll the audit log with a timeout (rows appear 53 to 72 s late).
  - **Extension bases (AD-31):** the bridge wraps every `OnEvent` call and never fails its caller. `Decide` runs `ReplyFilterClass` before recording anything. The three settings are read only through `Bridge.Ext.Accessor.ClassFor`, which never falls back silently.
  - **Rendering (AD-32):** producers never render text; they send a `CatalogKey` and JSON `Slots` (times UTC ISO 8601, counts integers, the item noun as `itemNoun: {"one","other"}`, model-written slots plain sentences with no times). Only `*Out` operations render, all through `Msg.Catalog.Render` (0.9), plus `TelegramIn`'s button-press alert; they add Approve and Reject only for kinds `incident` and `approval` with `ApprovalRef` set. The all-clear sentences are catalog entries only `Checks.Render` picks (AD-28).
- **AD-22 (testing and CI):**
  - `%UnitTest` classes live in `OcuTalon.Test.<Area>`, sharded by area, one compose project per shard, on the self-hosted runner; web and mock code runs on hosted runners. A pull request or a push to `main` runs everything. `OCUTALON_EVAL` passes through (default 0); only Lane A's evaluation job sets 1.
  - **The evaluation set** lives in `eval/<case>/` (`case.json` and `snapshot.json`, 0.10) as recorded Items and recorded reader snapshots, Lane A's after Epic 0; throwaways mount it read-only at `/opt/ocutalon/eval`. `EvidencePack.Build(source)` builds its pack from the live reader or a recorded snapshot.
  - **The mock (0.11)** is reached through the Anthropic provider's `base_url` over plain HTTP on the compose network, with no private CA or host alias (S3 passed). It answers `POST /v1/messages` and `GET /v1/models/<id>` (AI Hub's lookup when an agent starts), and rejects `temperature`, `top_p`, `top_k` and output caps under 4,000. Scenario choice: a `[[mock:<name>]]` marker in the newest user message with text, then a guide prompt's exact text contained in it (the `Agent.Input` preamble comes first), then the agent's `MOCKKEY`, never by wording. A summarizer request (`system` starting `OCUTALON-COMPACTION-V1`) gets AI Hub's summary schema (`facts_learned`, at least one `tool_actions` entry); one scenario answers off-schema. It logs header names and key length only; its only state is a per-test retry countdown, keyed by the test's marker and set through a control endpoint. One scenario sends a long `Retry-After` and asserts the wait is capped at the retry block's back-off (S18).
  - **Scenario files:** `ci/mock/scenarios/<A|B>/<name>.json` with `name`, `match` (`marker`, `prompt` or `mockkey`; `telegram`, a Bot API method name, from 10.3) and `replies` (each `status`, `headers`, `delayMs`, `stopReason`, and `text`, `toolUse` or `body`; a `telegram` reply uses a Bot API `body`). Lane A adds only files under `A/`; new mock behaviour is Lane B's, asked for under AD-33.
  - CI and scripts never run `docker compose config` without `--quiet` or `docker inspect` without `--format` (both print `env_file` values).

### Cross-lane contract obligations (AD-29, AD-33)

- **Contracts before code:** every release-1 contract gets its final names, types and storage; cross-lane APIs are signatures with stub bodies. Fully implemented in Epic 0: `Commands.Submit`, `Data.Public.Settings`, 0.4's helpers, 0.5's live-event store and API skeleton, `Msg.Catalog.Render` (0.9), and the Orders production with its real transform and one `eval/` snapshot (0.10). The owning lane appends the rest.
- **One owner each:** after Epic 0, each item, class, table and event type has one owning lane, and only it edits; the other lane asks. A new item, table or event type joins the ownership tables in the same change.
- **Lane A owns:** `OcuTalon.Bridge`, `.BridgeExample`, `.Agent`, `.Tools`, `.Watch`, `.Fix`, `.Checks`, `.Digest`, `.Eval`, `.Channel.Telegram`, `Msg.Catalog.Watch` and `eval/`; the installer core (the registry, `docker/merge.cpf`, and the role, user, SSL, task, `Production` and `Public` steps); `ci/mock/scenarios/A/`; `release/`; `.github/workflows/lane-a.yml`; and the demo path's Telegram parts from Epic 12.
- **Lane B owns:** `OcuTalon.Web` (with `.Web.Public`), the rest of `.Channel`, `.Core`, `.Schedule`, `.Demo`, `.Live`, `.Msg` (the renderer and `Catalog.Core` included), `.Data.Time`, `.Data.Setting`, `.Data.Ownership` and `.Data.Public`; `web/` (the demo-path runner configuration and fixtures included), the rest of `docker/` and `ci/` (the mock included), and `.github/workflows/ci.yml`; and the `Web` and `Demo` installer steps.
- **By area:** `OcuTalon.Test.<Area>`, `OcuTalon.Install.Step.<Area>` and `OcuTalon.Live.Payload.<Type>` (with its parts) follow their area's or publisher's lane.
- **Table owners:** Lane B: `Session`, `AddressCounter`, `StatusMark`, `GuideState`, `BreakFeedRun`, `Pairing`, `Turn`, `SimMessage`, `Delivery`, `Reminder`, `Setting` and `Live.Event`. Lane A: `BackgroundCheck`, `WatchMark`, `Incident`, `FailureGroup`, `FixRun`, `Digest.Data.Item` and every `Bridge.Data` class (`Decision`, `ApprovalRequest`, `Usage`, `Price`, `ConversationLink`, `ModelFamily`).
- **Production class:** one `ProductionDefinition` XData block, each lane's items between `<!-- lane A: begin -->`/`<!-- lane A: end -->` (the same for lane B), checked by `Test.Install.Production` and `.ProductionRules`. Every item is enabled except `TelegramIn` and `TelegramOut` (off until a release includes Telegram) and `EvalIn` (only with `OCUTALON_EVAL=1`). Unbuilt items answer "not implemented" and carry `STUB = 1`. Before a release cut, the owning lane disables, in its own region, any item whose story hasn't merged; 11.5 refuses an enabled stub.
- **`Decide` settings in Lane A's region:** `HostSinkClass` = `OcuTalon.Core.BridgeSink`, `ReplyFilterClass` = `OcuTalon.Checks.ReplyGuard`; `ClassificationClass` keeps the default until step 4.
- **HostSink payloads:** `decision.*` and `approval.*` carry `{ref}`, the record's public `Ref`; `turn.step` carries `{decisionRef, label}`, with the session as `ownerRef`; `budget.capped` has `ownerRef` `instance` and payload `{day}` (`YYYY-MM-DD`, instance zone).
- **Test-only global:** `^OcuTalonTest("TelegramIncluded")` is set only by `OcuTalon.Test` classes and never exists in the judges' install.

### Naming and storage conventions

- **Classes:** `OcuTalon.<Area>.<Name>`, one class per file. Cross-lane contracts go in `OcuTalon.Msg`/`OcuTalon.Data`, bridge contracts in `OcuTalon.Bridge.Msg`/`.Data`. Nothing under a system package name.
- **Item names:** PascalCase. Services end `In` (`FailurePoller` and `StatusMonitor` are the exceptions), channel operations end `Out`, and the Workflow operation is `OcuTalonApprovals`.
- **Messages:** extend `Ens.Request` or `Ens.Response`, with plain-English properties. Session-owned messages carry `SessionRef`, items carry `ItemId`. Rules route only on named properties. No names, user names or phone numbers are stored in production messages (AD-4); a session's `TraceRef` is the `SuperSession` of its messages and the demo tag on its Orders messages, whose bodies carry no `SessionRef`.
- **Enumerations:** defined once in `OcuTalon.Msg.Enum`; `OcuTalon.Bridge.Msg.Enum` copies only the seven the bridge uses, test-pinned equal. Enumeration-typed properties are plain `%String`, never `VALUELIST` copies. Display names live only in the catalog and the web app.
- **Identifiers:** every `Ref` (and `ItemId`, `SessionRef`, `TraceRef`) is a 22-character base64url string with no padding, from `OcuTalon.Bridge.Ids.NewRef()`. Row ids never leave the server; `Ens` header and session ids may, for trace links.
- **Times:** UTC ISO 8601 to the second, `YYYY-MM-DDThh:mm:ssZ`, in storage and the API; rendered only through `OcuTalon.Data.Time`. A message time is `Data.Time.ForMessage`'s (see 0.9).
- **Catalog keys:** `<prefix>.<name>`; every prefix lives in one catalog class, the class of the lane that owns the key's producer (Telegram's pairing replies and press alerts stay in `Catalog.Core`).
- **SQL reserved words:** a spine property name that is a reserved word keeps its name and gets an `SqlFieldName` (`Input` → `InputText`, `Count` → `FailureCount`).
- **REST:**
  - Paths `/ocutalon/api/v1/...`, plural nouns, commands as `POST` on a resource (`/approvals/:ref/answer`).
  - Errors are `{"error": {"code", "message"}}` in plain English: 400 `bad_cursor`; 401 `signed_out` (no `WWW-Authenticate`); 403 `no_role`, `not_json`, `no_request_header`, `wrong_origin`; 404 `not_found`; 405 `method_not_allowed`; 409 (already answered, not available); 429 (allowance, with `retryAt`); 500 `server_error`; 501 `not_built` for routes whose story hasn't shipped.
  - The live-event envelope is `{seq, stream, ts, type, payload}`, with camelCase payload keys.
- **Persistent classes:** every one that isn't a message or a business process sets `Parameter DEFAULTGLOBAL = ^OcuTalonP.<Short>` (`^OcuTalonBP.<Short>` in the bridge), with its row in `src/short-names.tsv` (one row per class, union-merged; CI fails on a duplicate). The compiler-generated `Storage` block is committed.
- **Settings keys:** product keys in `Data.Setting` are dotted (`digest.time`, `demo.mode`); `Setting.Get` serves the public keys from `Data.Public.Settings` uncached, and `Setting.Seed` refuses them.
- **Hosts and errors:** hosts log with `$$$LOGINFO`, `$$$LOGWARNING` and `$$$LOGERROR`. `%Status` throughout, `$$$ThrowOnError` inside methods, plain English only at the channel edge. Never read globals directly for settings.
- **Python:** only as `.py` resources under `src/ocutalon/python/`, never `[Language = python]`.
- **Angular:** standalone components and signals, hash routing, one typed API client and one live-event service; fonts and icons bundled with their licences, never from a CDN.
- **Tests:** `OcuTalon.Test.<Area>.<Subject>`, directly in the area folder; Playwright specs under `web/e2e/` (demo-path specs as 0.8 below); evaluation cases under `eval/<case>/`; mock scenarios `ci/mock/scenarios/<A|B>/<name>.json`.

## UX & Interaction Patterns

- **Built in Story 0.3:** the sign-in page and the app header (mark, wordmark, the "Demo mode" badge shown only with demo mode on locally, the account menu with Sign out). The main page is empty until 2.1.
- **Texts the public package keeps its own copies of** (`Login`'s and `ApiBase`'s parameters, among them the API's `no_role` and `signed_out` messages) must equal their `signIn.*` catalog keys; `Test.Web.PublicTexts` compares them.
- **Message text (the renderer applies these):** plain text, no Markdown; Telegram and the simulated phone share each text exactly and use words, never arrows. Times in message text are in the instance's zone, followed by "ET" on the online demo (page times are the browser's). Counts are digits, with singular and plural agreeing. Answered statuses name the channel as "the web chat", "the simulated phone" or "Telegram", and add "by <user>" only on a local install with more than one user. Quoted values take single quotes. An answered status ends with a period in message text; on the page it has none unless it holds two sentences.
- **The demo's orders:** Break the feed has the partner send the session's 50 orders "in a new date format"; the UX's dry run reads "Example: order date 10/16/2026 becomes 2026-10-16". So the failing field is the order date, and the item noun "order"/"orders". The transform's error text and the three Orders item names appear in the evidence panel and the fallback notice.
- **Token stylesheet:** generated from `DESIGN.md`'s front matter, with `<name>-dark` tokens. No text under 12px; icons hidden from assistive technology; `prefers-reduced-motion` stops all animation.

## Cross-Story Dependencies
