# Epic 22 Context: Extend OcuTalon with MCP servers, governed like built-in tools (step 4)

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Make tools from an admin-added MCP server into OcuTalon tools under the same governance as built-in ones: one gate, admin classification keyed by (server, tool name) and checked against the tool's fingerprint at every call, approval for anything risky or unclassified, and an audit entry and agent step for every call. Unclassified counts as risky, and a tool whose description or inputs change loses its classification. A hung server must never hold a runner: attach and listing are bounded now, and in the end OcuTalon lists and calls MCP tools through its own bounded client instead of AI Hub's. A read-only MCP tool can also be polled as a source, so new results become items and the source shows on the digest's coverage list. The epic ships a worked Jira example and an updated security overview, and adds a built-in email tool that sends to the user's own address without approval and holds any other recipient for approval. Adding an MCP server must never open a path around OcuTalon's governance.

## Requirements & Constraints

- **Online demo (standing Contest Planner rule):** real MCP servers never run on the online demo. Every MCP admin surface and every new kind is off on an online-demo install and refused with a plain reason. `McpOps` refuses every MCP verb there, no resource grants are declared, and no probe is ever sent; only the installer's allow-listed servers exist.
- Only admins add, remove or classify servers and tools, and only from the settings page (origin `web_admin`). No chat request, agent tool, item content, model output or tool result can do any of these. `McpOps` re-checks the origin behind `CommandsIn`'s refusal of origin `tool`.
- A new server's tools arrive Unclassified. Removing a server removes its tools at once (Story 22.2 restarts the runners and removes the entry, row, classifications and resource; Story 22.8 makes the gate deny any call to them) and cancels their pending approval requests (Story 22.4). Every add, remove and classification change is audited.
- Every MCP call, read-only ones included, gets an IRIS permission check, the pinned AI Hub policies, classification, approval when needed, an audit entry and an agent step. An automated test shows a risky MCP tool does not run without approval even when no platform policy covers it.
- A classification holds only for the fingerprint it was given for, checked at every call; tests show a rug-pull (same name, changed description or schema) is caught, including a change between the turn's listing and the call.
- MCP results are untrusted. They taint the turn (after that only read-only tools run), quarantine the next turn, and can never approve, classify, change settings or add servers. A Read-only MCP tool may run in an untrusted or tainted turn, but it still sends its arguments to its server; the governance docs must say so plainly (the sentence goes to the Contest Planner at Story 22.6's spec gate).
- An approved call runs exactly once, as approved. A replay with a changed fingerprint is refused and reported.
- All tool results of one model step together stay within 10,000 tokens, cut and marked as cut.
- MCP servers are reached only over `https://` (or loopback for development). A credential is stored only as a `secret://` IRIS Wallet reference. No command, log, test output, audit entry or record ever carries a secret value.
- Coverage: a source counts as checked only if its poll succeeded in the window; otherwise it shows as not checked with its reason (unreachable, error, timeout), and the digest gives no all-clear. Fixture wording: "Not checked: Jira (unreachable since 02:10). Everything else I checked passed."
- Documentation must say, in the same words in the worked example and the security overview, that an MCP tool that runs operating-system commands or arbitrary code must be classified risky. It must also document the mid-request residual (below) until Story 22.10 lands.

## Technical Decisions

- **Contracts already fixed (Epic 35, merged):** the verbs `AddMcpServer`, `RemoveMcpServer`, `ClassifyTool`, `SetSourcePoll` and `RemoveSourcePoll` are routed by `CommandsIn` to `McpOps`, and none carries a secret. `OcuTalon.Mcp.Server` holds `Name`, `CreatedAt`, `AttachStatus`, `AttachReason`, `AttachedAt` and `RefusedTools`. The runner attaches servers in `OnAfterAgentInit` as `mcp:remote:@{config:AI.MCP.OcuTalon_<server>}` through `McpServersClass` (`OcuTalon.Mcp.Attach`), and `McpOps` records each attach report on the row. Story 22.2 replaces the `Tools(server)` stub: an unknown server is an error; `status` is `unavailable` while `AttachStatus` is unavailable and `refused` when the name is in `RefusedTools`. Also in place: the mock MCP server, which binds loopback only, and `SettingsOps.RestartRunners()`. Story 22.2 also carries DW-1038: make the mock-dependent tests in `OcuTalon.Test.Mcp.Attach` robust under CI load.
- **Writes:** `McpOps` (a production item from Story 22.2, sole writer of `Mcp.Server` and `Mcp.ToolClassification`) writes the row and the classification rows, then calls `RestartRunners()`. `SettingsOps.SaveMcpEntry` and `RemoveMcpEntry` write the wallet secret and the `AI.MCP.OcuTalon_<server>` Config Store entry. Those writes never happen in the REST process: a later ruling has them run from `McpOps`'s production job, delivered with Lane B's Story 21.4, and until then the routes are stubs. Check the current spine before choosing the call site.
- **Per-server resource:** `OcuTalon_MCP_<server>` (no public permission) and its `U` grant to `OcuTalonServiceRole` are created on add and removed with the server only through one fixed entry point, `OcuTalon.Install.Step.Mcp.Grant(server)` / `Revoke(server)` (only `Install.*` reaches `%SYS`). It acts only on a name `OcuTalon_MCP_` plus a valid server name, and a unit test shows it refuses any other. It runs in `McpOps`' production job with that job's existing privilege: no new privilege (`%Admin_Secure`, `%All` or any security administration) for the service role or `McpOps`. `Install.Step.Mcp.Grants()` re-declares the grants at every start from the `Mcp.Server` rows.
- **Fingerprints at attach (Story 22.2):** the attach report carries `fingerprints` (tool name to `OcuTalon.Bridge.Context.ToolFingerprint(description, parameters)`, a hash of the canonical description and input schema). `McpOps.RecordAttach` keeps one `ToolClassification` row per discovered tool (refused ones included), deletes rows of tools no longer listed, clears a classified tool whose fingerprint changed through `McpOps.ClearChanged` (audited), and sends `mcp.serverUnavailable`, `mcp.toolShadowsBuiltIn` and `mcp.toolChanged` (kind `status`) once per transition.
- **Gate (`OcuTalon.Bridge.Policy.Gate`):** it recognises an MCP call first, by a `toolref` starting `mcp:`, before `metadata.origin_class`, so a tool that shadows a built-in never takes the built-in's class; annotations such as `readOnlyHint` are ignored. Story 22.8: before `Chat`, the runner builds the turn's fingerprint map from the serving manager's `%Discover()` (`ComposeTurnTools`) into the bridge context (node `mcp`). The gate classifies through `ClassificationClass.ClassifyMcp(source, name, fingerprint)`, returning `classification`, `readOnly`, `registered` (the default delegates to `Classify` with readOnly 0, registered 1; OcuTalon names `OcuTalon.Mcp.Classification` on `Decide`). A tool missing from the map, without a row, unclassified, or whose fingerprint does not match its classification's counts as risky. A toolref whose server is not registered is denied with `UNREGISTERED` before every other step, replays included. A change found at turn start is cleared through `McpOps.ClearChanged`; the gate repeats the clear if that failed. An admin's read-only gives readOnly 1. The gate fails closed (missing context, exception or lock timeout means deny) and catches its own exceptions. Open risk DW-174: measure a real MCP tool's toolref and metadata in `%CanExecute` (stdio, remote, JSON configuration form of `%AI.Tool.Resolver`).
- **Read-only judgement (DW-724, Story 22.8):** `McpServersClass` gains `ToolsReadOnly(server) As %Boolean` (default 0); `Decide.ToolsReadOnly` requires it for every listed server, so an unclassified or non-read-only MCP tool means the agent is not read-only.
- **Bounded attach and listing (Story 22.9, DW-1013):** measured: AI Hub gives no deadline (against a server that accepts and never answers, `AddTool` blocked 632 s, `%Discover()` 551 s, a built-in tool's `ExecuteTool` 300 s); `MCPDescriptor` takes no timeout key; every listing and tool call lists every MCP server on the manager; `$SYSTEM.Process.Terminate` waits for the native call. So the agent's own manager holds no MCP server. `McpServersClass` gains `Probe(server, config) As %String` (default `""`, no probe; OcuTalon: `OcuTalon.Mcp.Client.Probe`, an unauthenticated JSON-RPC `initialize` with a 2 s limit, sent only to admin-registered servers). The build attaches each server to a report-only manager after the probe; each request's manager adds only servers whose probe answered. A failed probe reports the server `unavailable` (reason `unreachable`) and rests it 60 s per runner job; per-request reports go out on transitions. Agents that declare skills get no MCP tools. A failed attach's error text can contain the resolved credential, so it only picks a reason word and is never logged or stored.
- **Mid-request residual:** a server that stops answering after its probe passed, within the same request, still holds that runner job until it closes the connection. Accepted for this release; Story 22.6 documents it and Story 22.10 removes it by amending AD-21's "AI Hub lists, OcuTalon calls" rule: OcuTalon's own Streamable HTTP client (22.3's, with 22.9's bounds) does both listing and calling, AI Hub's MCP client is no longer used for either, and gate, fingerprint classification, approval and audit apply unchanged.
- **Governed proxy (Story 22.3):** the gate rewrites every allowed MCP call into `call_mcp_tool(server, tool, arguments)`, OcuTalon's minimal Streamable HTTP client (`initialize`, `tools/call`). Just before `tools/call` it re-lists the tool with its own client and refuses the call, unrun, if the fingerprint no longer matches the classified one. Its result goes through `OcuTalon.Tools.Result`. A direct call to `call_mcp_tool` is classified by its (server, tool) arguments. Add `call_mcp_tool` and the email tool to `OcuTalon.Tools.Names` and to the CI mock's scripts.
- **Permissions:** the gate checks the service user's permission on `OcuTalon_MCP_<server>` with `$SYSTEM.Security.CheckUserPermission`.
- **Approval:** the request is `Approval.Raise` kind `tool_call` with the exact call (server, tool, canonical arguments) plus the fingerprint, and no dry run. The model gets a plain denial sentence that reads well after AI Hub's prefix. On approval, `ApprovalHold` sends a `tool` request through `Decide` to the runner that made the call, which runs `StartExecution`, sets a one-use grant, calls `ExecuteTool` through the full policy chain, routes the call to `call_mcp_tool` and records `FinishExecution`. A replay with no grant, or a second replay, gets `ToolAccessDenied`. The conversation gets a code-written note on its next turn, never the result text. Row state changes only through the Approval API, and removal cancels pending requests with `Approval.Cancel`.
- **Source polls:** a `BackgroundCheck` row of `Kind` `source`, owned by the admin's session, holding the server, tool, arguments (JSON), interval and `DisplayName`, created and removed only through `OcuTalon.Watch.Ops`'s row methods, which `McpOps` calls after refusing a tool that is not read-only; `McpOps` then sends `CheckChanged`. `Checks` stays the writer of the run fields (last run, result, trace header id) and publishes `check` events. A poll runs as a `tool` request through `Decide` with no model. New results become untrusted Items to `Intake`, de-duplicated. A tool that becomes unclassified or risky stops polling.
- **Email tool (Story 22.7):** classification comes from a `Classify(arguments)` class method that the gate calls in place of the class parameters (this extends the spine's tool-classification convention). A safe call submits `SendEmail` through `Commands.Submit` (origin `tool`, idempotency key), and `CommandsIn` itself checks that every recipient is the session's `email.address`. A risky call raises fix kind `OcuTalon.Fix.Kind.Email` (DryRun keys `to`, `subject`, `text`; target `EmailOut`; no `IncidentRef`; `ResultTarget` `FixExecutor`). `FixExecutor` sends once with origin `system` from the approved row only and sends no `FixResult` to `IncidentManager`.
- **Audit:** `OcuTalon.Bridge.Audit` is the only writer, and entries pass the redactor. Tests read entries back from the IRIS audit log with polling.
- **Notices:** producers never render text. Admin notices use catalog keys in `OcuTalon.Msg.Catalog.Watch` (`mcp.serverUnavailable`, `mcp.toolShadowsBuiltIn`, `mcp.toolChanged`), read the attach report on the `Mcp.Server` row, and reach `Ownership.AdminSessions()`, with no run-time `%SYS` read. The email fix's notices come from `OcuTalon.Core.BridgeSink`.
- **Lane A owns** `OcuTalon.Mcp`, `.Tools`, `.Watch`, `.Fix`, `.Checks`, `.Digest`, the bridge, `ci/mock/scenarios/A/`, and in `docs/` the security overview. Tests are `%UnitTest` classes under `OcuTalon.Test.<Area>` against the loopback mock MCP server.

## UX & Interaction Patterns

- Settings › Tools and MCP servers (Lane B builds it) shows each tool as Unclassified (risky), Read-only or Risky, saved at once and audited. A changed tool reverts to Unclassified and the admins get a notice card. Only read-only tools can be source polls.
- A tool-call approval card reads "Run {tool} on {server}" with the exact inputs, plus the no-dry-run sentence. An email fix's dry run shows the exact text and every recipient.
- In an untrusted or tainted turn, a non-read-only suggestion (including an email) is described to the user as an offer and is never raised as a request.
- The agent step label names the server and tool, never the arguments.
