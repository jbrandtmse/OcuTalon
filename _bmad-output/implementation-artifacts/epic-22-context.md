# Epic 22 Context: Extend OcuTalon with MCP servers, governed like built-in tools (step 4)

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Make tools from an admin-added MCP server into OcuTalon tools under the same governance as built-in ones: one gate, admin classification keyed by (server, tool name) and checked against the tool's fingerprint at every call, approval for anything risky or unclassified, and an audit entry and agent step for every call. Unclassified counts as risky, and a tool whose description or inputs change loses its classification. A hung server must never hold a runner: attach and listing are bounded first, and in the end OcuTalon lists and calls MCP tools through its own bounded client instead of AI Hub's. A read-only MCP tool can also be polled as a source, so new results become items and the source shows on the digest's coverage list. The epic ships a worked Jira example and an updated security overview, and adds a built-in email tool that sends to the user's own address without approval and holds any other recipient for approval. Adding an MCP server must never open a path around OcuTalon's governance.

## Requirements & Constraints

- **Online demo (standing rule):** real MCP servers never run on the online demo. Every MCP admin surface and new kind is off there and refused with a plain reason; `McpOps` refuses every MCP verb, no resource grants are declared, no probe is sent, and `call_mcp_tool` is never offered (refused with `MCPDEMO`). Only the installer's allow-listed servers exist.
- Only admins add, remove or classify servers and tools, and only from the settings page (origin `web_admin`). No chat request, agent tool, item content, model output or tool result can do any of these; `McpOps` re-checks the origin behind `CommandsIn`'s refusal of origin `tool`.
- New tools arrive Unclassified. Removing a server removes its tools at once (runners restarted, entry, row, classifications and resource removed; the gate denies calls to it) and cancels its pending approval requests. Every add, remove and classification change is audited.
- Every MCP call, read-only ones included, gets the IRIS permission check, the pinned AI Hub policies, classification, approval when needed, an audit entry and an agent step. An automated test shows a risky MCP tool does not run without approval even when no platform policy covers it.
- A classification holds only for the fingerprint it was given for, checked at every call; tests show a rug-pull (same name, changed description or schema) is caught, including a change between the turn's listing and the call.
- MCP results are untrusted: they taint the turn (then only read-only tools run), quarantine the next turn, and can never approve, classify, change settings or add servers. A Read-only MCP tool may run in an untrusted or tainted turn but still sends its arguments to its server; the governance docs must say so plainly (sentence goes to the Contest Planner at Story 22.6's spec gate).
- An approved call runs exactly once, as approved; a replay with a changed fingerprint is refused, never run, and reported.
- All tool results of one model step together stay within 10,000 tokens, cut and marked as cut.
- MCP servers are reached only over `https://` (or loopback for development), with the server certificate verified. A credential is stored only as a `secret://` IRIS Wallet reference; no command, message body, Visual Trace, log, test output, audit entry or record ever carries a secret value.
- Coverage: a source counts as checked only if its poll succeeded in the window; otherwise it shows as not checked with its reason (unreachable, error, timeout) and the digest gives no all-clear. Fixture wording: "Not checked: Jira (unreachable since 02:10). Everything else I checked passed."
- Docs must say, in the same words in the worked example and the security overview, that an MCP tool that runs operating-system commands or arbitrary code must be classified risky, and must document the mid-request residual until Story 22.10 lands.

## Technical Decisions

- **Fingerprint form:** `OcuTalon.Bridge.Context.ToolFingerprint(server, name, description, parameters)` is SHA-256 hex over a canonical, sorted-keys form of the server id (its `tool_ref`), tool name, description and input schema. The same form is used at attach, in the turn map, by the proxy's call-time re-list and on approval rows.
- **In place (Epic 35, Stories 22.2 and 22.8):** the five verbs (`AddMcpServer`, `RemoveMcpServer`, `ClassifyTool`, `SetSourcePoll`, `RemoveSourcePoll`; none carries a secret) route to `McpOps` (`OcuTalon.Mcp.Ops`, a production item, sole writer of `Mcp.Server` and `Mcp.ToolClassification`), which writes rows and calls `SettingsOps.RestartRunners()`. `Tools(server)` is built. The per-server resource `OcuTalon_MCP_<server>` and its `U` grant to `OcuTalonServiceRole` go only through `OcuTalon.Install.Step.Mcp.Grant/Revoke(server)` (name-checked; no new privilege for the service role or `McpOps`), re-declared at start by `Grants()`. The attach report carries `fingerprints`; `McpOps.RecordAttach` keeps one row per discovered tool, clears changed ones through `McpOps.ClearChanged` (audited), and sends `mcp.serverUnavailable`, `mcp.toolShadowsBuiltIn`, `mcp.toolChanged` once per transition. The mock MCP server binds loopback only (keep-alive -1, queue size 5).
- **Wallet and Config Store writes** never happen in the REST process: Lane B's Story 21.4 moves them into `McpOps`; until then the settings routes are stubs.
- **Gate (`OcuTalon.Bridge.Policy.Gate`, done in 22.8):** an MCP call is recognised first by a `toolref` starting `mcp:`, before `metadata.origin_class`; annotations such as `readOnlyHint` are ignored. Before `Chat` the runner builds the turn's fingerprint map from the serving manager's `%Discover()` (`ComposeTurnTools`, bridge context node `mcp`). The gate classifies through `ClassificationClass.ClassifyMcp(source, name, fingerprint)` (`classification`, `readOnly`, `registered`, optional `resource`; OcuTalon: `OcuTalon.Mcp.Classification`). Missing from the map, no row, unclassified or fingerprint mismatch counts as risky; admin read-only gives readOnly 1 (result still taints). An unregistered server's toolref is denied `UNREGISTERED` before every other step, replays included. The gate fails closed and catches its own exceptions. `McpServersClass.ToolsReadOnly(server)` (default 0) feeds `Decide.ToolsReadOnly` (DW-724).
- **Bounded attach and listing (22.9):** measured, AI Hub has no deadline (`AddTool` 632 s, `%Discover()` 551 s, `ExecuteTool` 300 s against a silent server), `MCPDescriptor` takes no timeout, every listing and call lists every MCP server on the manager, and `$SYSTEM.Process.Terminate` waits for the native call. So the agent's own manager holds no MCP server. `McpServersClass.Probe(server, config)` (default `""`; OcuTalon: `OcuTalon.Mcp.Client.Probe`, unauthenticated JSON-RPC `initialize`, 2 s limit, admin-registered servers only). The build attaches each server to a report-only manager after the probe; each request's manager adds only servers whose probe answered. A failed probe reports `unavailable` (reason `unreachable`) and rests the server 60 s per runner job; per-request reports go out on transitions. Agents that declare skills get no MCP tools. A failed attach's error text can hold the resolved credential, so it only picks a reason word and is never logged or stored.
- **Mid-request residual:** a server that stops answering after its probe passed, within one request, still holds that runner job until it closes the connection. Accepted for now; 22.6 documents it; 22.10 removes it by amending AD-21's "AI Hub lists, OcuTalon calls" so OcuTalon's own client (22.3's, with 22.9's bounds) does both listing and calling, gate, fingerprint classification, approval and audit unchanged.
- **Governed proxy (22.3):** the gate rewrites every allowed MCP call into `call_mcp_tool(server, tool, arguments)`, offered only by a request's composed manager that holds an MCP server, through `McpServersClass.ProxyToolSet()` (default `""`); it is in no agent's `TOOLSETS`. Its client extends `OcuTalon.Mcp.Client` (bounds: 2 s `initialize`, 2 s `tools/list`, 20 s `tools/call`), sets `VerifyPeer` (plain `http://` only to this computer), and re-lists the tool just before `tools/call`, refusing a changed fingerprint unrun. Results go through `OcuTalon.Tools.Result`, taint the turn and are cut. One `MCP` audit entry per run (`called` or `refused`: server, tool, outcome only). The proxy never writes the classification row. A direct call to `call_mcp_tool` is classified by its (server, tool) arguments. Permission: MCP and proxy calls check the service user's `U` on the `resource` `ClassifyMcp` answers, via `$SYSTEM.Security.CheckUserPermission`. If the gate cannot reroute a native call it denies it with `MCPUSEPROXY` and the model calls `call_mcp_tool` itself (pre-approved fallback); Task 0 measures and records the reroute mechanism. Add `call_mcp_tool` and the email tool to `OcuTalon.Tools.Names` and the CI mock's scripts.
- **Approval and replay (22.4):** `Approval.Raise` kind `tool_call` with the exact call (server, tool, canonical arguments); an `mcp:` row requires `ToolFingerprint` (`Raise` refuses one without it); no dry run; the model gets a plain denial sentence that reads well after AI Hub's prefix. On approval, `ApprovalHold` sends a `tool` request through `Decide` to the calling runner, which runs `StartExecution`, sets a one-use grant and replays as `call_mcp_tool {server, tool, arguments}` on a governed manager holding only `ProxyToolSet()`, swapped in for the call with the agent's own manager restored on every path. The grant matches on (tool, canonical arguments, toolref), the toolref taken from the grant only when `McpServersClass.ServerOf(toolref)` (default `""`) equals the call's server. The proxy runs only at the row's fingerprint; a change ends `FinishExecution` with result `changed`, which `Core.BridgeSink` maps to `mcp.replayToolChanged`. No grant or a second replay gets `ToolAccessDenied`. The conversation gets a code-written note on its next turn, never the result text. `McpOps` calls `Approval.CancelPending(source, …)` after a removal commits.
- **Source polls (22.5):** a `BackgroundCheck` row of `Kind` `source`, owned by the admin's session (server, tool, arguments JSON, interval, `DisplayName`), created and removed only through `OcuTalon.Watch.Ops`'s row methods, called by `McpOps` after refusing a non-read-only tool; `McpOps` then sends `CheckChanged`. `Checks` writes the run fields and publishes `check` events. A poll runs as a `tool` request through `Decide` with no model; new results become de-duplicated untrusted Items to `Intake`. A tool that turns unclassified or risky stops polling.
- **Email tool (22.7):** a `Classify(arguments)` class method the gate calls in place of class parameters (extends the tool-classification convention). Safe: `SendEmail` through `Commands.Submit` (origin `tool`, idempotency key), with `CommandsIn` checking every recipient is the session's `email.address`. Risky: fix kind `OcuTalon.Fix.Kind.Email` (DryRun `to`, `subject`, `text`; target `EmailOut`; no `IncidentRef`; `ResultTarget` `FixExecutor`); `FixExecutor` sends once with origin `system` from the approved row and sends no `FixResult` to `IncidentManager`.
- **Audit:** `OcuTalon.Bridge.Audit` is the only writer; entries pass the redactor; tests poll the IRIS audit log.
- **Notices:** producers never render text; catalog keys live in `OcuTalon.Msg.Catalog.Watch` and reach `Ownership.AdminSessions()` with no run-time `%SYS` read. Tool-call and email-fix approval notices come from `OcuTalon.Core.BridgeSink`.
- **Lane A owns** `OcuTalon.Mcp`, `.Tools`, `.Watch`, `.Fix`, `.Checks`, `.Digest`, the bridge, `ci/mock/scenarios/A/` and the security overview in `docs/`. Tests are `%UnitTest` classes under `OcuTalon.Test.<Area>` against the loopback mock MCP server. Open risk DW-174: measure a real MCP tool's toolref and metadata in `%CanExecute`.

## UX & Interaction Patterns

- Settings › Tools and MCP servers (Lane B) shows each tool as Unclassified (risky), Read-only or Risky, saved at once and audited; a changed tool reverts to Unclassified with an admin notice card. Only read-only tools can be source polls.
- A tool-call approval card reads "Run {tool} on {server}" with the exact inputs and the no-dry-run sentence. An email fix's dry run shows the exact text and every recipient.
- In an untrusted or tainted turn, a non-read-only suggestion (email included) is described as an offer, never raised as a request.
- The agent step label names the server and tool, never the arguments.
