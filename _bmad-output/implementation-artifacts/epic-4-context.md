# Epic 4 Context: The demo page: guide, simulated phone and mailbox, and Break the feed

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Demo mode turns the signed-in page into the self-guided two-minute demo: a demo guide with one-click prompts, a labelled simulated phone and simulated mailbox that are real production channels, and a Break the feed control that makes the simulated partner send the session's 50 orders in a changed date format, which fail for real in the Orders production. The server derives guide progress and Break the feed availability from what really happened in the session, so the demo claims nothing it didn't do, contains nothing canned, and can be run again. An admin switches demo mode from the terminal; with it off, none of this exists and nothing else changes. Lane B; depends on Epic 2.

## Stories

- Story 4.1: Switch demo mode from the terminal (done)
- Story 4.2: Derive the guide state and Break the feed availability on the server (done)
- Story 4.3: Break the feed with a real batch of 50 orders (done)
- Story 4.4: Show the demo guide and the Break the feed box
- Story 4.5: Get notifications on the simulated phone
- Story 4.6: Simulate incoming email in the simulated mailbox
- Story 4.7: Finish the demo guide

## Requirements & Constraints

- **Demo mode** defaults on for `docker compose up` and off for IPM, and a switch survives restarts and upgrades. Only `OcuTalonAdmin` may switch (`%All` alone is refused); every switch is audited and applies within 60 s, and the page picks it up at its next `/state` load (no settings live event).
- **Demo mode off:** no context badge or demo feature, demo endpoints answer 404, nothing routes to the phone, and the conversation, rail and history are unchanged; OCUORDERS and the Orders production are removed (a foreign OCUORDERS is kept, with the `demoKept` mark).
- **Nothing canned:** sample emails are inputs decided live; incident text comes from the real failures; mocks exist only in CI's configuration, never in the judges' compose file.
- **Simulated devices:** each carries a visible "Simulated" label and is a real channel (Visual Trace looks the same; only the channel name differs). The phone shows the session's notifications only, in the paired chat's catalog text (plain text, no Markdown or emoji, instance-zone times with " ET" online), and has no composer. Mailbox emails are untrusted items decided live: Ignore and Digest notify nobody, only Tell now or Act notifies, and an email never makes OcuTalon act.
- **Break the feed:** active only while the session watches Orders and no Orders incident is open (any variant, until dismissed), awaiting approval or fixing, and no run under 3 minutes old is still without a notice. Two quick presses send one batch. A resolved incident is closed first, so every run opens a new incident with its own approval request. Concurrent sessions each get exactly 50 failures tagged with their own `TraceRef`, and no shared partner state changes. A press is a production message, never a turn: no `Turn`, no decision, no allowance use; audited as an `Action`.
- **The guide:** a step is done only from real state (1: an Orders watch; 2: a reminder, pending or fired; 3: the incident, fallback or no-fix notice in the current run; 4: its approval answered; 5: the trace-opened marker). The finish shows only after an approved fix and a resolved incident; after a fallback, no-fix or rejection the guide keeps the matching step 4 hint and shows no finish text. Run again resets the guide's markers only, never the session's data.
- **Timing:** against the mock, a tell-now notification reaches the phone within 5 s of its decision (Story 4.5 turns on this half of Story 2.7's CI check); live updates arrive within 2 s. NFR-7's 60 s from press to notice and the demo-path time budget are measured in the rehearsal, not asserted in CI.

## Technical Decisions

- **Demo mode (4.1, built).** `demo.mode` ("1"/"0") in `Data.Setting`, read via `Setting.Get` (60 s per-process cache). `Core.Admin.SetDemoMode(mode)` checks the value, then `OcuTalonAdmin` in `$ROLES`, and submits `SetDemoMode` (with `ActingUser`) as origin `system`; `SettingsOps`, the only run-time settings writer, audits, saves, and reruns `Install.Step.Demo.Run()` on every accepted command.
- **Spine edges.** `Core --> Install.Step.Demo.Run()` (only `SettingsOps`, on a switch; AD-23); `Guide --> Telegram.In.Included()`; `Demo --> Install.Step.Demo` for its constants (`MODEKEY`, `NAMESPACE`, `PRODUCTION`), read by `Guide`, `BreakFeedIn` and `PartnerTrigger`. Web and Data (with Live) call Guide. Demo, Live and Data have no edge to Core, so `Guide.DemoOn` repeats `Core.Rule.Functions.DemoOn`.
- **Orders.** `Install.Step.Demo` (Epic 4's file) owns OCUORDERS and starts the non-autostart Orders production itself; it never stops another production. Only `PartnerTrigger.Send` and the Demo step switch namespace (one `New $NAMESPACE` method each). Items run `PartnerOrdersIn` → `OrdersFromPartner` (Epic 0's real transform) → `OrdersToWarehouse`. Orders bodies carry no `SessionRef`; the session's `TraceRef` is their `SuperSession`. Edit only the production class's Lane B region.
- **How state changes.** Only through business services; adapterless ones via `Ens.Director.CreateBusinessService` and `ProcessInput`, which works from the REST process, `SendRequestSync` included. REST writes only `GuideState`'s UI markers. `IncidentManager` (Lane A) is the only incident writer; ownership reads hide an incident until its notice sets `NoticedAt`, and before that only `watch.progress` (`noticed`, `settling`, `diagnosing`, keyed by the incident's `Ref`) goes out.
- **The guide (4.2, built).** `Demo.Guide.Compute(SessionRef)` is the single source (rows via `Data.Ownership`, the markers, the clock); `/state`'s `guide` (last key, demo on only) and `guide.state` carry it, and the page never decides any of it. `Guide.Blank()` is the no-rows view.
  - Payload: `runEpoch`, `step`, `finished`, `steps`, `breakFeed` (`active`, `reason`, `stage`, `startedAt`), `step4Variant`, `telegramRow`. Closed snake_case values: reason `not_watching` | `incident_in_progress`; stage `sending`, `waiting`, `still_waiting` (from 90 s), `no_notice` (from 180 s; frees the control), `notice_arrived` (first in this order wins: `notice_arrived`, `no_notice`, `sending`, `still_waiting`, `waiting`); variant `paired` | `unpaired` | `rejected` | `fallback` | `no_fix`. `stage` and `startedAt` are empty while the session doesn't watch Orders. This is not `breakfeed.progress`, the run row's own view (`State`, `StartedAt`; `live-store.ts` keeps the latest).
  - The current run starts at the epoch's latest run or the epoch's start; steps 3-4, the variant and the finish read the newest Orders incident noticed in it. With variant `rejected`, `fallback` or `no_fix`, a current step 5 becomes 4. `expired` gives paired/unpaired (no UX text exists; Story 4.7 may revisit). Availability reads the latest run of any epoch; the stage only the current epoch's.
  - `Live.Publish.RefreshGuide` is the one `guide.state` publisher, publishing only on a change and bounded by its caller's lock wait (so `BridgeSink`'s 1 s bound holds for any new trigger publisher). Callers: the `Publish` hook (demo on) after the seven `GUIDETRIGGERS` (`chat.message`, `incident`, `approval`, `check`, `reminder`, `pairing`, `breakfeed.progress`; not `turn.step`), `StatusMonitor.GuideTick()` (runs started in the last 240 s) and the marker endpoint.
  - `GuideState` holds `TraceOpened`, `RunEpoch` (1 with no row) and `RunStartedAt`. `POST /api/v1/guide/markers` with `{"marker":"trace_opened"|"run_again"}` answers 200 with the guide view; 404 demo off, 400 `MESSAGEBADMARKER`, else 500.
  - "Telegram is on" means `Telegram.In.Included()` is 1 and `Guide.TelegramState()` is `on` (a literal `off` until Story 10.3); the paired variant needs it.
- **Break the feed (4.3, built).** `POST /api/v1/demo/break-feed` (body not read; session from the CSP session) answers, in order: 404 `not_found` (demo off), 500 (no readable session), 409 `{"error":{"code":<reason>,"message":<hint>}}` with the exact hints "Ask OcuTalon to watch the Orders production first (step 1)." and "Finish the current Orders incident first: approve or reject its fix, or dismiss the incident.", 200 `{"state":"sent","startedAt"}`, else 500 `server_error`.
  - `Web.Api` hands a `Demo.Press` to `BreakFeedIn`, which under `LOCK ^OcuTalon.Demo.BreakFeed(SessionRef)` (a timeout is `incident_in_progress`) checks `Guide.Compute().BreakFeed`, closes the session's own noticed resolved Orders incidents (`closeForReplay`, sync; a refusal is 409), writes `BreakFeedRun` `sending` and publishes `breakfeed.progress`, sends `Demo.Msg.SendOrders` to `PartnerTrigger` (sync), then marks the run `sent` and publishes again. `PartnerTrigger` audits the `Action` (a failed audit sends nothing), then sends 50 `MM/DD/YYYY` orders tagged with the `TraceRef`.
  - A sync send with no answer is an error: `SendRequestSync` returns OK with no response on a timeout, so every synchronous target must answer (`PartnerTrigger` an `Ens.Response`). A failed send leaves the run `sending` until the 180 s rule frees the control (no `failed` state, no retry).
  - Until Epic 5's Story 5.5 builds `closeForReplay`, a real session with a resolved Orders incident gets a 500; tests use `Test.Demo.IncidentManagerDouble`.
- **Channels (4.5, 4.6).** `Notify` routes to the web chat, to `SimPhoneOut` (demo on only) and to the paired chat; kind `allowance` never reaches the phone. Only `*Out` operations render, through `Msg.Catalog.Render(key, slots, channel)` with channels `phone` and `mailbox`. Each `*Out` records a `SimMessage`, records its `Delivery` via `Data.Delivery.Record(ownerRef, channel, channelMessageId, approvalRef)`, and publishes `phone` (from `SimPhoneOut`) or `mailbox` (from `SimMailboxOut`). `SimMailboxIn` records the arriving `SimMessage` with the item's `ItemId`, publishes `mailbox`, and sends an `OcuTalon.Msg.Item` (channel `mailbox`, provenance `untrusted`) to `Intake`; the row finds its decision by that `ItemId`, which the decision event carries. Nothing routes to `SimMailboxOut` in release 1, so its test uses a fixture message.
- **Audit and Epic 3 (merged at the integrate-forward `3d76632`).** Product code audits only through `Bridge.Audit.Record(type, data)`, with the type's fixed shape and every member set; `Record` redacts itself, so don't redact twice. `Test.Bridge.CodeRules` `TestOnlyTheAuditWriterAudits` fails any other audit `Write` (Story 4.1 needed a rework for this). Types used here: `Settings` for demo mode (data names `ActingUser`) and `Action` for Break the feed (`action, target, result, counts, approvalRef, irisUser, sessionRef, channel`). Tests read entries with `Test.Bridge.AuditLog`, polling with a timeout. Epic 3 also brought the governance gate, which emits `turn.step` (Story 3.2), and approvals held in IRIS Workflow.
- **Data and conventions.** Lane B owns `GuideState`, `BreakFeedRun`, `SimMessage`, `Delivery`, `Setting`, `StatusMark` and `Live.Event`. Other epics' rows (`BackgroundCheck`, `Incident`, `ApprovalRequest`, `Decision`, `Usage`, `Reminder`) are read only through `Data.Ownership` with the caller's `SessionRef`; no endpoint accepts a `SessionRef` from the client, and product code never writes Lane A rows. Storage is append-only with storage blocks committed; a private class sets `DEFAULTGLOBAL` `^OcuTalonP.<Short>` and registers it in `src/short-names.tsv`. Refs from `Bridge.Ids.NewRef()`; times UTC ISO 8601, rendered only through `Data.Time`. Live payloads are full views keyed by `Ref`, published after commit, one publisher per type; TS types come from `web/scripts/payloads.mjs`, page texts from `web/scripts/catalog.mjs`.
- **REST.** Under `/ocutalon/api/v1`; errors are `{"error":{"code","message"}}` in plain English. A route answers 501 `not_built` until its story ships and 404 while demo mode is off; a mailbox field error answers 400. State-changing calls need `application/json`, `X-OcuTalon-Request: 1` and a matching `Origin`.
- **Testing.**
  - `%UnitTest` classes live in `OcuTalon.Test.<Area>` (doubles in `OcuTalon.Test.Demo`), lane-b shard via `ci/iris.sh`. Probe subclasses override private seams called through `..` (as `GuideProbe`, `BreakFeedInProbe` do). `Test.Demo.Step` saves and restores `demo.mode`; `Test.Data.Fixture` makes rows and cleans them and their messages. Real batches, the real production and item swaps (`RunnerFixture.UseItemClass`) run only on lane-b fresh throwaways, guarded like `Test.Demo.Production`. A test creates the state it relies on (such as an enabled audit event) and puts it back.
  - The real `StatusMonitor` ticks every 15 s on the test stack: a test that needs demo mode off switches it off before creating rows. On a warm stack a running job keeps the old compiled class: toggle the item or use a fresh stack.
  - Pinned surfaces: a route or `/state` key change updates `Test.Web.Api` (`TestStateBody`, `TestRoutes`), `web/e2e/api/api.spec.ts` (`UNBUILT`, exact keys) and `web/e2e/frame/frame.spec.ts` F9; a payload change `Test.Live.Payloads` and `payloads.mjs --check`; a table change `Test.Data.Tables` and `test-storage.sh`; a stub item made real its `"stub"` row in `Test/Core/ProductionItems.cls`. `web/scripts/playwright-projects.test.mjs` pins the Playwright projects (`chromium` takes every spec outside `demo-path/`, `demo-switch/` and `floor/`, each of which runs only its own folder; every spec belongs to a project): update it for any new e2e folder.
  - `live:demo-switch` (`docker/tests/test-demo-switch.sh`, Epic 4's own script; `image` group and `BROWSER_UNITS`) is the destructive switch check; it runs the Playwright `demo-switch` project (`guide.spec.ts`, relative assertions) with only `OCUTALON_URL` and `OCUTALON_E2E_DEMO_MODE` set. `docker/tests/test-demo-path.sh` is contended (Epics 10 and 13): don't edit it. `web/e2e/support/iris.ts` finds the IRIS container by `OCUTALON_URL`'s published port when `OCUTALON_E2E_IRIS_CONTAINER` is unset, so `irisScript` works in the demo-path run.
  - Demo-path specs are `web/e2e/demo-path/0<n>-<id>.spec.ts`; an unbuilt part stays a `notBuilt(title, 'N.M')` call, and a turned-on test that must never skip again carries `@floor`. `04-incident` holds 4.3's `@floor` press test (a fixture Orders watch for README via `irisScript` stands in for Epic 5's watch; assertions relative to the cursor) and its two `11.1` parts. Floor specs (`web/e2e/floor/`) run only in `live:floor`.
  - The mock matches the two guide prompts by their exact text (scenarios under `ci/mock/scenarios/B/`); mailbox tests pick outcomes with `[[mock:<name>]]` markers. A keyless throwaway falls back to `tellnow`/`no_key`, so tests that need real outcomes use `RunnerFixture.PointKeys` and `RestoreKeys`. Never switch keys on the shared `live:sign-in` stack.

## UX & Interaction Patterns

- **Layout.** The "Demo guide" region sits between the banners and the rail and chat, with the Break the feed box at its right, over the device column. The "Simulated devices" region sits right of the chat at `device-width` (wider from 1440 px). Under 680 px tall the guide uses its compact single row; from 1024 to 1279 px wide steps show numbers; under 1024 px the page stacks into one column.
- **The guide.** Steps are buttons, selectable in any order. Markers: a check for done, a teal disc for current, a hollow circle for upcoming, a 2 px bottom bar for the selected step (never a teal ring). The current step has `aria-current="step"`, and each step's name includes its state. When a step completes, the guide advances by itself, moves focus to the prompt bar's action and announces "Step {n} of 5: {step}". "Hide guide" collapses it to a bar whose "Show guide" button has `aria-expanded`; the choice is remembered per browser.
- **Guide prompts** are sent verbatim as the user's own chat message with `fromGuide`, shown with the display-only caption "From the demo guide": each is a real turn with a decision and a trace, and counts toward the allowance.
- **The Break the feed box** always shows the "Demo control" label. An inactive button stays focusable with `aria-disabled`, its visible hint linked by `aria-describedby`. The reason gives the hint, the stage the box line, `startedAt` the elapsed time, and `watch.progress` the noticed/settling/diagnosing lines. Progress lines never show counts, and the box is not a live region.
- **The devices.** ARIA tabs (arrow keys, `aria-selected`) that never switch by themselves: new content puts a badge count in the tab's name, and a switch the user causes (such as the guide's Show me) is allowed. The selected tab is remembered per browser. The amber "Simulated" label is static and unfocusable. The phone is a generic frame (no clock, carrier, brand or Telegram look), not a live region, and doesn't auto-scroll while the user has scrolled up or an approval is pending (the "New messages" pattern applies).
- **The mailbox.** Sample chips are always visible; pressing one keeps focus on it and announces the new row. The compose form replaces the list, with focus on From. A row has an unread dot with hidden "Unread", shows "Deciding…" then the outcome chip, and announces the decision; it opens in place with focus on the subject heading, and Back returns focus to the row. Untrusted text renders only as text.
- **Shared rules.** The page speaks only through `Announcer`. Focus moves only when an update removed the focused element (`shared/focus-rule.ts`). Links that leave the page say "(opens in a new tab)". Prompts, hints, box states, empty states, sample emails and the finish text are exact: take them verbatim from the stories and the UX.
