# Epic 3 Context: Nothing risky happens without a yes, and everything is audited

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Epic 3 (Lane A) builds OcuTalon's governance core in the bridge and the installer. One fail-closed gate classifies every tool call as safe or risky by fixed rules that neither the model nor arriving content can change, and content that didn't come from the user can only look, notify and save. Each risky action becomes one IRIS Workflow approval request, fixed to exact targets, answered once (the first answer wins), expiring after 24 hours and surviving restarts. Every action and governance event goes to the IRIS audit log through one writer, and the roles and the service user decide who may do what. The epic also lands the online demo's public settings, password guard and $20 daily cap early, so the online-demo epics can make November 1. The approved tool-call replay is not in this epic (it moved to Epic 30): here a risky tool call is held and runs nothing.

## Stories

- Story 3.1: Roles and the service user grant only what the architecture lists (done)
- Story 3.2: One gate decides every tool call (done)
- Story 3.3: Content that didn't come from the user can only look, notify and save (done)
- Story 3.4: Each risky action becomes one approval request held in IRIS Workflow (done)
- Story 3.5: The first answer wins, and unanswered requests expire (done)
- Story 3.6: A risky tool call waits for approval and runs nothing
- Story 3.7: Every action and governance event is in the IRIS audit log
- Story 3.8: The online demo's settings, password guard and spending cap are ready

## Requirements & Constraints

- **No risky action runs without an approved request**, in every configuration.
  - Safe: read-only checks and tools; setting, listing or cancelling reminders; saving for the digest; messages to the user; starting or stopping a background check the user asked for.
  - Risky: any change to a production, its items, settings or messages; anything sent to someone other than the user; any risky or unclassified tool. Unclassified counts as risky.
- **Untrusted content** leads only to read-only checks, notifying the user and saving for the digest; anything else is offered to the user in plain words, and an offer never becomes an approval request. No built-in tool can answer an approval, classify a tool, change a setting, add an MCP server or pair a chat.
- **One test per risky built-in tool** shows it doesn't run when a user's turn calls it; the suite fails if one is missing. A rejected or expired request runs nothing.
- **Approval requests:** targets and the exact change are fixed when raised, and carrying one out calls no model. The first answer wins, and the loser learns which channel won and when. A request expires 24 hours after it is raised and can then be neither approved nor started. Pending requests survive restarts and in-place upgrades. On a local install the required role defaults to `OcuTalonUser`.
- **Audit entries** carry time, IRIS user and session for: an action run (target, result), an approval answered (who, channel, outcome), a pairing, a settings change, an MCP server added or removed, a tool classified. No entry holds a key, token, password, or Telegram chat id or display name. If instance-wide auditing is off, say so plainly (log warning plus a recorded status); never change that setting.
- **Privileges:** roles and the service user hold only what the architecture lists. The public accounts can change nothing, including their own passwords.
- **Online-demo budget:** the daily cost cap defaults to $20, and the gateway's spend counts toward today. At the cap, a decision falls back with `daily_cap` before any request is sent.
- **Routed open items:**
  - DW-187 (3.6): Raise's `ApprovalStartIn` `ProcessInput` commits every open transaction level of the caller, and the hold's job can't see an uncommitted row; measure `$TLevel` inside `%CanExecute` before the gate calls Raise. The five state methods also assume no open transaction.
  - DW-191 (3.6): that `ProcessInput` runs in the caller's job and replaces its session and current header ids, so the gate's later event-log rows would lose the runner's session; restore them after the call, or start the hold another way.
  - DW-10 (3.7), the warning when instance-wide auditing is off; DW-160 (3.8), see the `Public` step below.

## Technical Decisions

**The gate**, `OcuTalon.Bridge.Policy.Gate` (3.2, 3.3), an AI Hub Authorization policy the runner adapter adds beside the step audit policy in `OnAfterAgentInit`:
- It runs for every tool call and **fails closed**: a missing context, an exception or a lock timeout means deny, always as a caught `ToolAccessDenied` status (an escaping exception skips the audit policies and leaks a source line to the model).
- **`Decision`'s order:** call checks (`FAILED`), classification, permissions (`NOPRIVILEGE`), provenance and taint (`UNTRUSTED`), then the result: a `safe` call is allowed and every other call is denied with `NEEDSAPPROVAL`, the placeholder 3.6 replaces with the hold. The gate takes no lock yet; Raise's lock is the first on its path, so 3.6 tests the lock timeout through it.
- **Classification by (source, name):** built-in tools by class parameters (`CLASSIFICATION`, `READONLY`, `TRUSTEDOUTPUT`, optionally suffixed `<NAME>`) or an `[ Internal ]` `Classify<NAME>`/`Classify(arguments)`; a developer's own tools by Decide's `ToolClassification` setting (a JSON array of `{class, tool, classification}`), which never overrides code; then `ClassificationClass`. An `mcp:` source uses `ClassificationClass` alone. A call's metadata, arguments and context never classify it.
- **Permissions:** a tool's `RESOURCES` (`resource:permission[,…]`) is checked for Decide's `ServiceUser` (default `OcuTalonService`) with `$SYSTEM.Security.CheckUserPermission`, before provenance and before any hold.
- **Provenance and taint (3.3):** a turn is untrusted when `Provenance` isn't exactly `user`, and tainted when `Tainted` isn't 0. There only safe, read-only calls run; every other call is denied with `UNTRUSTED`, fires no `turn.step` and never reaches the result branch, so steered content can never raise an approval. An allowed call fires `turn.step` (`{decisionRef, label}`, the session as `ownerRef`) through `HostSinkClass`, then taints the turn unless the tool's `trustedOutput` is 1.
- **Callbacks** (gate, tools, renderer, host sink) never call AI Hub's native `%AI` agent, session, tool-manager or provider methods (that deadlocks the job; a CI check flags it). `Test.Bridge.CodeRules.ToolCodeClean` flags any tool reference to governance (the Approval API, `AnswersIn`, `EnsLib.Workflow`, settings writers, production-changing calls); approval code stays in the bridge, and 3.6 adds `Approval` to `CodeRules`' `CALLBACKHELPERS`.
- **Governance tests:** built-in tools go through a real `%AI.ToolMgr` with no model; developer test tools run end to end through a shadow runner of `ZzGateAgent` (toolsets `ZzGateTools`, `ZzGateInjection`) and the mock. 3.3's approval-row counts (an untrusted turn; the suspicious-request email, which must trigger no resend, setting change or approval) can't fail until 3.6 raises approvals; 3.6 makes them live.

**Approvals:** `OcuTalon.Bridge.Approval`; the row is the truth. 3.4 built Raise, the hold, the Workflow setup and Reconcile; 3.5 built `Answer`, `Expire`, `Cancel`, `StartExecution`, `FinishExecution`, `HoldResponse` and `Msg.ApprovalOutcome`, so no Epic 0 stub is left.
- **Constants** are `Approval` parameters (`WORKFLOWROLE`, `WORKFLOWUSER`, `STARTITEM`, `HOLDITEM`, `ACTIONS`, `TASKSUBJECT`, `EXPIRYSECONDS`, `LOCKSECONDS`, `STARTSECONDS`, `TASKSECONDS` = 5). The required role comes from `Decide`'s host setting `ApprovalRole` (category Bridge, default `OcuTalonUser`, read through `Ext.Accessor.ValueFor`); an empty value refuses Raise.
- **`Raise(request, Output ref, sinkClass, sessionId, superSession)`** validates an unsaved row (refusing any field that Raise or the state methods own), then under `LOCK +^OcuTalon.Bridge.Approval(Ref)` sets `Ref`, `pending`, `RequiredRole`, `RaisedAt` and `ExpiresAt` (+24 h), saves, and starts the hold synchronously through `ApprovalStartIn`, so OK means held. A failed Raise (refusal, lock timeout, failed or timed-out start) deletes its row and leaves no hold and no event. `approval.raised` fires once after the unlock.
- **Targets and change** are the row's contract columns: `ToolName` and `ToolArguments` for `tool_call`; `DryRun` (AD-16's keys) for `fix`, whose message scope is the failure group its `IncidentRef` names. No new column.
- **Trace session**, each value on its own: `sessionId` argument, else the bridge context's `ThreadSessionId`, else new; `superSession` argument, else the context's `SuperSession`, else the row's `TraceRef`. `ApprovalStartIn` sets `..%SessionId` and `..%SuperSession`, calls the hold with `SendRequestSync(HOLDITEM, …, STARTSECONDS)`, and returns an error when no answer arrives.
- **`ApprovalHold`** stores only `Ref`; `OnRequest` and `OnResponse` are one line each, calling `Approval.Hold` and `Approval.HoldResponse` (AD-5; `TestHoldIsFrozen` pins it). `Hold` sends the `TaskRequest` ("Approve,Reject", subject `TASKSUBJECT` plus the Ref, no `%UserName`) to `OcuTalonApprovals` with completion key `task`, and sets timer key `expiry` to the whole seconds until `ExpiresAt` (at least 1). The framework deletes a finished hold.
- **Workflow and restarts:** `Bridge.Installer.SetUpApprovals` keeps the login-disabled, role-less `OcuTalonWorkflow` the only member of `OcuTalonApprovals`; no person or public account is a Workflow user. A live hold survives restarts; `Install.Step.Approvals.Reconcile()` (every start) cancels orphan tasks and re-arms each pending row without a live hold, in its own session tagged with `TraceRef`, timed from `ExpiresAt`.
- **State changes** go only through the five methods, each under `LOCK +^OcuTalon.Bridge.Approval(Ref)` with a wait of `LOCKSECONDS + TASKSECONDS` (7 s), on a row `LockedRow` re-reads under the lock (a caller's held copy never decides). `pending` → `approved`/`rejected` (Answer), `expired` (Expire, or Answer past expiry), `cancelled` (Cancel, which also completes the task with no action, so the hold ends with no outcome); `approved` → `executing` (StartExecution, only while `ExpiresAt` is ahead, checked and set together) → `done` or `failed` (FinishExecution `done`, or `failed`/`interrupted`); `approved` → `failed` (FinishExecution `failed` only). FinishExecution sets `Result` and `FinishedAt`. Any other pair, a missing row or a Ref that isn't 22 characters is an error naming the Ref and the state; a refusal changes no column and fires no event. `Expire` never compares the clock (DW-186): its callers, the hold's timer and Answer's past-expiry step, decide the time is up.
- **`Answer(ref, action, channel, irisUser, sessionRef, Output winner, sinkClass)`** checks in order: no row or a `cancelled` row → `not_found`; an action other than `approve`/`reject`, a channel outside `Msg.Enum` `CHANNEL`, or a user without the row's `RequiredRole` → `not_allowed`; an `expired` row → `expired`; an answered row → `already_answered`, `winner` `{action, channel, at}`; a pending row at or past `ExpiresAt` becomes `expired` (its task left for the timer) → `expired`; otherwise it saves `AnsweredAction`, `AnsweredChannel`, `AnsweredBy`, `AnsweredAt` and the state, then completes the newest open task with the Ref's subject as `OcuTalonWorkflow` (waiting up to `TASKSECONDS`) → `done`. A lock not taken or a failed save records nothing → `not_found`; a task that never comes is a warning and the answer stands. `sessionRef` is accepted for 3.7's audit entry and not stored.
- **The role check** reads `$SYSTEM.Security.GetUserRecursedRoleSet(irisUser)`, names compared without case; an error or an empty `RequiredRole` holds nobody. Another user's set needs `%Admin_Secure:USE`: production jobs have it, a CSP job only for its own `$USERNAME`.
- **Events** fire after the unlock through `Decide.FireEvent`, from the job that made the change, with the row's `OwnerRef` and `HostSink.RefPayload(ref)`, to `sinkClass` (a trailing optional argument) else `HostSinkClass`: `approval.answered` (Answer `done`), `approval.expired` (Expire, in the hold's job on its timer; Answer past expiry), `approval.cancelled`, `approval.result` (FinishExecution); StartExecution fires nothing.
- **Outcomes:** `HoldResponse` on key `expiry` first calls `Expire`, then sends only what the row shows: on `task`, the TaskResponse's action must match an `approved` or `rejected` row; on `expiry`, the row's `expired`, `approved` or `rejected` state (so an answer whose task couldn't be completed is delivered by the timer). It sends `Msg.ApprovalOutcome` (`Ens.Request`: `ApprovalRef`, `IncidentRef`, `Outcome` approved/rejected/expired) with `SendRequestAsync` to the row's `ResultTarget` in the hold's session. An empty `ResultTarget` sends nothing; an approved `tool_call` sends nothing until Story 30.3's replay, so it runs nothing. A failed send is logged and the hold still ends.
- **The hold in the gate (3.6):** only in the result branch of a user's turn, a risky or unclassified call calls `Raise` (kind `tool_call`, the exact call) from inside `%CanExecute`, in the bridge context, then denies with "held for your approval; nothing was run". A failed Raise leaves nothing and the call is still denied. A row with no `ResultTarget` gets no outcome on rejection or expiry. The NFR-13 tests use `Answer` (reject) and `Expire` to show a rejected or expired request runs nothing.

**Audit (3.7):** `OcuTalon.Bridge.Audit` is the only writer, through `$SYSTEM.Security.Audit`, source `OcuTalon`, types `Action`, `Approval`, `Pairing`, `Settings`, `MCP`, `Tool`, one fixed data shape per type; `Bridge.Installer` registers the events on every start. Production jobs run as the Interoperability system user, so event data names the acting IRIS user, `SessionRef` and channel. Every entry passes `OcuTalon.Bridge.Redact`. 3.4 and 3.5 left Raise and the five state methods unaudited; 3.7 audits every change the five methods make, with `Answer`'s `irisUser`, `channel` and `sessionRef`. There is no OcuTalon audit table: tests read the IRIS audit log back, polling with a timeout (rows can land minutes late), through a reusable helper in `OcuTalon.Test.Bridge`.

**Roles and accounts (3.1):** `OcuTalonService` is login-disabled with no services and exactly `OcuTalonServiceRole`, a privilege profile the gate checks. No role holds `%All`, `%Development`, `%Ens_MessageEditResend`, `%Ens_MessageDiscard`, `%Ens_ProductionRun`, `%Ens_ProductionConfig`, `%Ens_WorkflowConfig` or the Workflow inbox. The Users step reads the online-demo flag and accounts only through `OcuTalon.Data.Public.Settings`; `Users.PinTrace` pins a public account's Visual Trace page size to 100.

**The `Public` step and the budget (3.8):**
- Runs right after `Bridge.Installer`, before roles, users and web applications. On every start it writes the fixed public keys from the online-demo environment variables, only through `OcuTalon.Data.Public.Settings` (Lane B owns it; a CI check fails any other reference to its global), with readiness cleared. Without `OCUTALON_ONLINE_DEMO` it writes only the flag (off) and readiness.
- Online demo only, before `Production`: writes `Decide`'s System Default Settings `DailyCostCapUSD` (default 20; 0 = off), `GatewaySpendUSD` and `GatewaySpendDate` (instance-zone date). On a local install `DailyCostCapUSD` is a seed value 0 and the gateway values aren't written. The bridge never reads public settings; `Budget.State()` and `Decide`'s precheck read the three through the bridge's settings accessor.
- Its last phase, after `Production` and `Reconcile` and before `SetReady`, calls `Users.PinTrace` for both public accounts, because on a fresh flag-on volume OCUORDERS doesn't exist yet when Users runs (DW-160).
- **Password guard** (online demo only): a password-validation routine allows each public account only its published password, with the user name compared case-insensitively, without blocking the installer's own write.

**Conventions:**
- The bridge references no other OcuTalon package (CI-enforced); it reaches its host only through the extension classes and settings on `Decide`. A failed `OnEvent` is logged and never fails the caller. Storage is append-only, with committed storage blocks.
- Governance tests are `%UnitTest` classes in `OcuTalon.Test.Bridge`, run in the `lane-a` shard: 44 classes, about 420 to 450 s fresh after 3.5, against a 500 s split line and a 10-minute job cap; keep tests lean.
- Approval tests reuse `Test.Bridge.Approval`'s helpers (`NewRow`, `Raise`, `WaitTask`, `WaitHoldGone`, `WaitHoldSettled` before any "nothing sent" or event count, `Complete`, `Age`, `WaitState`, `JustNow`, `AssertOneOutcome`, the job body and the lock gate `WaitWaiters` for concurrency, never a sleep) and its Ref tracking under `^OcuTalonTest("Approval")`. They answer as the README account `ocutalon` (holds `OcuTalonUser`), create no IRIS user, and keep no `ApprovalRequest` object across a hold's change. `ProbeSink`'s calls carry the row's `State` at the call as an eighth element; its `rowExists` counts approval rows.
- Role, user, security and Workflow changes and test runs happen only on throwaway stacks through `ci/iris.sh`; the developer slot is load-and-compile only. Tests restore every security object, setting and public key they change. Lane A extends the CI model mock only under `ci/mock/scenarios/A/`.

## UX & Interaction Patterns

- **Denials are plain sentences the model relays.** The model sees AI Hub's prefix ending "Tool access denied: " before each sentence, so sentences start in lower case and read well after it; each is a gate class parameter, and the sentences stay distinct. A held call: "held for your approval; nothing was run". An untrusted or tainted turn: only read-only tools can run, and the model describes the action as an offer the user can ask for in their own turn.
- **Answer statuses:** `Answer`'s results and `winner` feed channel statuses such as "Approved from Telegram at 14:15" and "Already answered: …". The bridge never renders user-facing text.
- **The turn indicator** shows the tool's readable label from `turn.step`; a label never holds arguments or model text.
