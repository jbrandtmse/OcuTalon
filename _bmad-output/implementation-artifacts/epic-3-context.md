# Epic 3 Context: Nothing risky happens without a yes, and everything is audited

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Epic 3 (Lane A) builds OcuTalon's governance core in the bridge and the installer. One fail-closed gate classifies every tool call as safe or risky by fixed rules that neither the model nor arriving content can change, and content that didn't come from the user can only look, notify and save. Each risky action becomes one IRIS Workflow approval request, fixed to exact targets, answered once (the first answer wins), expiring after 24 hours and surviving restarts. Every action and governance event goes to the IRIS audit log through one writer, and the roles and the service user decide who may do what. The epic also lands the online demo's public settings, password guard and $20 daily cap early, so the online-demo epics can make November 1. The approved tool-call replay is not in this epic (it moved to Epic 30): here a risky tool call is held and runs nothing.

## Stories

- Story 3.1: Roles and the service user grant only what the architecture lists (done)
- Story 3.2: One gate decides every tool call (done)
- Story 3.3: Content that didn't come from the user can only look, notify and save (done)
- Story 3.4: Each risky action becomes one approval request held in IRIS Workflow (done)
- Story 3.5: The first answer wins, and unanswered requests expire (done)
- Story 3.6: A risky tool call waits for approval and runs nothing (done)
- Story 3.7: Every action and governance event is in the IRIS audit log
- Story 3.8: The online demo's settings, password guard and spending cap are ready

## Requirements & Constraints

- **No risky action runs without an approved request**, in every configuration.
  - Safe: read-only checks and tools; setting, listing or cancelling reminders; saving for the digest; messages to the user; starting or stopping a background check the user asked for.
  - Risky: any change to a production, its items, settings or messages; anything sent to someone other than the user; any risky or unclassified tool. Unclassified counts as risky.
- **Untrusted content** leads only to read-only checks, notifying the user and saving for the digest; anything else is offered to the user in plain words, and an offer never becomes an approval request. No built-in tool can answer an approval, classify a tool, change a setting, add an MCP server or pair a chat.
- **Approval requests:** targets and the exact change are fixed when raised, and carrying one out calls no model. The first answer wins, and the loser learns which channel won and when. A request expires 24 hours after it is raised and can then be neither approved nor started. Pending requests survive restarts and in-place upgrades. On a local install the required role defaults to `OcuTalonUser`. A rejected or expired request runs nothing.
- **Audit entries** carry time, IRIS user and session for: an action run (target, result), an approval answered (who, channel, outcome), a pairing linked, unlinked or rejected, a settings change, an MCP server added or removed, a tool classified. No entry holds a key, token, password, or Telegram chat id or display name. If instance-wide auditing is off, the `Audit` step says so plainly (DW-10: a log warning plus a recorded status the security overview and README can point to); OcuTalon never changes that setting.
- **Privileges:** roles and the service user hold only what the architecture lists. The public accounts can change nothing, including their own passwords.
- **Online-demo budget:** the daily cost cap defaults to $20, and the gateway's spend counts toward today. At the cap, a decision falls back with `daily_cap` before any request is sent.
- **Open items:** DW-10 (3.7) and DW-160 (3.8), below. Routed elsewhere: DW-194 (Story 30.3: a held row stores neither the tool's source class nor the runner); a hold whose start times out after `STARTSECONDS` can still create its task and timer after Raise has deleted the row (deferred, medium, unverified; 3.4's path).

## Technical Decisions

**The gate**, `OcuTalon.Bridge.Policy.Gate` (3.2, 3.3, 3.6), an AI Hub Authorization policy the runner adapter adds beside the step audit policy in `OnAfterAgentInit`:
- It runs for every tool call and **fails closed**: a missing context, an exception, a lock timeout or a failed Raise means deny, always as a caught `ToolAccessDenied` status (an escaping exception skips the audit policies and leaks a source line to the model).
- **`Decision`'s order:** call checks (`FAILED`), classification, permissions (`NOPRIVILEGE`), provenance and taint (`UNTRUSTED`), then the result: a `safe` call is allowed and every other call is held. A failed check, a missing privilege or an untrusted or tainted turn never raises a request.
- **Classification by (source, name):** built-in tools by class parameters (`CLASSIFICATION`, `READONLY`, `TRUSTEDOUTPUT`, optionally suffixed `<NAME>`) or an `[ Internal ]` `Classify<NAME>`/`Classify(arguments)`; a developer's own tools by Decide's `ToolClassification` setting (a JSON array of `{class, tool, classification}`), which never overrides code; then `ClassificationClass`. An `mcp:` source uses `ClassificationClass` alone. A call's metadata, arguments and context never classify it.
- **Permissions:** a tool's `RESOURCES` (`resource:permission[,…]`) is checked for Decide's `ServiceUser` (default `OcuTalonService`) with `$SYSTEM.Security.CheckUserPermission`, before provenance and before any hold.
- **Provenance and taint:** a turn is untrusted when `Provenance` isn't exactly `user`, and tainted when `Tainted` isn't 0. There only safe, read-only calls run; every other call is denied with `UNTRUSTED` and fires no `turn.step`. An allowed call fires `turn.step` (`{decisionRef, label}`, the session as `ownerRef`) through `HostSinkClass`, then taints the turn unless the tool's `trustedOutput` is 1.
- **The hold (3.6):** the gate builds an unsaved `ApprovalRequest` (`Kind` `tool_call`; `ToolName`; `ToolArguments` as given: an object's `%ToJSON()`, a non-blank JSON text verbatim, absent or `null` as `{}`, while an array, number or boolean denies with `FAILED`; `OwnerRef` and `TraceRef` from the context; no `ResultTarget`, `IncidentRef` or `DryRun`) and calls `Raise(row, .ref, sinkClass)` from inside `%CanExecute`; the session and SuperSession come from the context.
  - Raise OK: denied with `HELD`, no `turn.step`, no taint, and Raise's `approval.raised` is the only event.
  - A failed Raise: `FAILED` plus `Check`'s one redacted warning naming the tool, its source and the error; it never says held.
  - Each held call is its own request (no de-duplication). With no `ResultTarget` the hold sends no outcome; the user learns the answer through the HostSink events. The held call writes no audit entry.
- **Callbacks** (gate, tools, renderer, host sink) never call AI Hub's native `%AI` agent, session, tool-manager or provider methods (that deadlocks the job). `CodeRules`' `CALLBACKHELPERS` holds the classes Raise runs inside the callback (`Approval`, `Service.ApprovalStart`, `Ids`, `Time`, `Data.ApprovalRequest`, `Msg.ApprovalStart`); `BridgeSink`'s future callees aren't scanned (DW-177). `Test.Bridge.CodeRules.ToolCodeClean` flags any tool reference to governance (the Approval API, `AnswersIn`, `EnsLib.Workflow`, settings writers, production-changing calls).
- **Governance tests:** built-in tools go through a real `%AI.ToolMgr` with no model; developer test tools run end to end through a shadow runner of `ZzGateAgent` (toolsets `ZzGateTools`, `ZzGateInjection` with seven tools) and the mock. One test per risky built-in tool shows it doesn't run in a user's turn; the suite fails if one is missing. Gate tests track every OwnerRef under `^OcuTalonTest("Gate","owners")`; the cleanup before and after each test ends and deletes their rows through `Test.Bridge.Approval`'s `Clean`, and `OnAfterOneTest` asserts none is left. A tool's run is marked in `^OcuTalonTest("Gate","ran",<name>)`.

**Approvals:** `OcuTalon.Bridge.Approval`; the row is the truth. 3.4 built Raise, the hold, the Workflow setup and Reconcile; 3.5 the five state methods, `HoldResponse` and `Msg.ApprovalOutcome`; 3.6 the gate's hold.
- **Constants** are `Approval` parameters (`WORKFLOWROLE`, `WORKFLOWUSER`, `STARTITEM`, `HOLDITEM`, `ACTIONS`, `TASKSUBJECT`, `EXPIRYSECONDS`, `LOCKSECONDS`, `STARTSECONDS`, `TASKSECONDS` = 5). The required role comes from `Decide`'s host setting `ApprovalRole` (category Bridge, default `OcuTalonUser`, read through `Ext.Accessor.ValueFor`); an empty value refuses Raise.
- **`Raise(request, Output ref, sinkClass, sessionId, superSession)`** refuses at `$TLevel` above 0 before writing anything (the error names `$TLevel`; the caller's transaction stays open), because `ApprovalStartIn`'s `ProcessInput` would commit it (DW-187). It validates an unsaved row (refusing any field Raise or the state methods own), then under `LOCK +^OcuTalon.Bridge.Approval(Ref)` sets `Ref`, `pending`, `RequiredRole`, `RaisedAt` and `ExpiresAt` (+24 h), saves, and starts the hold synchronously, so OK means held. A failed Raise deletes its row and leaves no hold and no event. `approval.raised` fires once after the unlock.
- **`StartHold`** sets the trace session (argument, else the context's `ThreadSessionId`/`SuperSession`, else new, tagged with `TraceRef`), sends to the hold with `SendRequestSync(HOLDITEM, …, STARTSECONDS)`, and afterwards puts back the job's `$$$JobSessionId` and `$$$JobCurrentHeaderId` (also after an error or exception), so a host job's later log rows keep their session (DW-191). `Reconcile` calls it directly, outside Raise's `$TLevel` guard (it runs at level 0).
- **Targets and change** are the row's contract columns: `ToolName` and `ToolArguments` for `tool_call`; `DryRun` for `fix`, whose message scope is the failure group its `IncidentRef` names.
- **`ApprovalHold`** stores only `Ref`; its `OnRequest` and `OnResponse` each call `Approval.Hold` and `Approval.HoldResponse` (AD-5). `Hold` sends the "Approve,Reject" `TaskRequest` to `OcuTalonApprovals` (completion key `task`) and sets timer key `expiry` from `ExpiresAt`. `Bridge.Installer.SetUpApprovals` keeps the login-disabled, role-less `OcuTalonWorkflow` the only member of `OcuTalonApprovals`. `Install.Step.Approvals.Reconcile()` (every start) cancels orphan tasks and re-arms each pending row without a live hold.
- **State changes** go only through the five methods, each under `LOCK +^OcuTalon.Bridge.Approval(Ref)` with a wait of `LOCKSECONDS + TASKSECONDS` (7 s), on a row `LockedRow` re-reads under the lock. `pending` → `approved`/`rejected` (Answer), `expired` (Expire, or Answer past expiry), `cancelled` (Cancel, which also completes the task with no action); `approved` → `executing` (StartExecution, only while `ExpiresAt` is ahead) → `done` or `failed` (FinishExecution `done`, or `failed`/`interrupted`); `approved` → `failed` (FinishExecution `failed` only). FinishExecution sets `Result` and `FinishedAt`. Any other pair, a missing row or a Ref that isn't 22 characters is an error naming the Ref and the state; a refusal changes no column and fires no event. `Expire` never compares the clock: the hold's timer and Answer's past-expiry step decide the time is up.
- **`Answer(ref, action, channel, irisUser, sessionRef, Output winner, sinkClass)`** checks in order: no row or a `cancelled` row → `not_found`; a bad action, a channel outside `Msg.Enum` `CHANNEL`, or a user without the row's `RequiredRole` (recursed role set, names compared without case; another user's set needs `%Admin_Secure:USE`, which production jobs have) → `not_allowed`; an `expired` row → `expired`; an answered row → `already_answered`, `winner` `{action, channel, at}`; a pending row at or past `ExpiresAt` becomes `expired`; otherwise it saves `AnsweredAction`, `AnsweredChannel`, `AnsweredBy`, `AnsweredAt` and the state, then completes the task → `done`. A lock not taken records nothing → `not_found`. `sessionRef` is accepted for 3.7's audit entry and not stored.
- **Events** fire after the unlock through `Decide.FireEvent`, from the job that made the change, with the row's `OwnerRef` and `HostSink.RefPayload(ref)`, to `sinkClass` else `HostSinkClass`: `approval.answered` (Answer `done`), `approval.expired` (Expire in the hold's job on its timer; Answer past expiry), `approval.cancelled`, `approval.result` (FinishExecution); StartExecution fires nothing.
- **Outcomes:** `HoldResponse` sends `Msg.ApprovalOutcome` (approved/rejected/expired) only when the row already shows it, to the row's `ResultTarget` in the hold's session. An empty `ResultTarget` sends nothing; an approved `tool_call` sends nothing until Story 30.3's replay.

**Audit (3.7):**
- `OcuTalon.Bridge.Audit` is the only writer, for the bridge and OcuTalon, through `$SYSTEM.Security.Audit`, source `OcuTalon`, types `Action`, `Approval`, `Pairing`, `Settings`, `MCP`, `Tool`, one fixed data shape per type. It declares the events (`Bridge.Audit.Events()`), which `Bridge.Installer` registers in its one `%SYS` method at every install and start.
- Production jobs run as the Interoperability system user, so event data names the acting or answering IRIS user, the `SessionRef` and the channel, and the entry carries its time. Every entry passes `OcuTalon.Bridge.Redact`.
- Raise, the five state methods and 3.6's held call are unaudited so far. 3.7 audits every change `Answer`, `Expire`, `Cancel`, `StartExecution` and `FinishExecution` make (with `Answer`'s `irisUser`, `channel` and `sessionRef`); the action entry of an approved run comes with Story 30.3's replay.
- There is no OcuTalon audit table: tests read the IRIS audit log back, polling with a timeout (rows can land minutes late), through a reusable helper in `OcuTalon.Test.Bridge`.
- DW-10: the `Install.Step.Audit` step's warning and recorded status when instance-wide auditing is off.

**Roles and accounts (3.1):** `OcuTalonService` is login-disabled with no services and exactly `OcuTalonServiceRole`, a privilege profile the gate checks. No role holds `%All`, `%Development`, `%Ens_MessageEditResend`, `%Ens_MessageDiscard`, `%Ens_ProductionRun`, `%Ens_ProductionConfig`, `%Ens_WorkflowConfig` or the Workflow inbox. The Users step reads the online-demo flag and accounts only through `OcuTalon.Data.Public.Settings`; `Users.PinTrace` pins a public account's Visual Trace page size to 100.

**The `Public` step and the budget (3.8):**
- Runs right after `Bridge.Installer`, before roles, users and web applications. On every start it writes the fixed public keys from the online-demo environment variables (AD-19's list; connection cap, reserve and message allowance default to 8, 2 and 50 an hour), only through `OcuTalon.Data.Public.Settings.Set` (Lane B owns it; a CI check fails any other reference to its global), with readiness cleared. Without `OCUTALON_ONLINE_DEMO` it writes only the flag (off) and readiness.
- Online demo only, before `Production`: writes `Decide`'s System Default Settings `DailyCostCapUSD` (default 20; 0 = off), `GatewaySpendUSD` and `GatewaySpendDate` (instance-zone date). On a local install `DailyCostCapUSD` is a seed value 0 and the gateway values aren't written. The bridge never reads public settings; `Budget.State()` and `Decide`'s precheck read the three through the bridge's settings accessor.
- Its last phase, after `Production` and `Reconcile`, calls `Users.PinTrace` for both public accounts (on a fresh flag-on volume OCUORDERS doesn't exist yet when Users runs; DW-160), then sets readiness with `SetReady`.
- **Password guard:** with the flag set, the Users step installs a password-validation routine that allows each public account only its published password, the user name compared case-insensitively, without blocking the installer's own write; none on a local install.

**Conventions:**
- The bridge references no other OcuTalon package (CI-enforced); it reaches its host only through the extension classes and settings on `Decide`. A failed `OnEvent` is logged and never fails the caller. Storage is append-only, with committed storage blocks.
- Governance tests are `%UnitTest` classes in `OcuTalon.Test.Bridge`, run in the `lane-a` shard: 44 classes, 405 s fresh after 3.6, against a 480 s line and a 10-minute job cap; keep tests lean.
- Approval tests reuse `Test.Bridge.Approval`'s public helpers (`NewRow`, `Raise`, `TrackOwner`, `WaitTask`, `WaitHoldSettled` before any "nothing sent" or event count, `Complete`, `Age`, `WaitState`, `HoldMessages`, `HoldRequests`, `HoldCount`, `StartsSince`, `Clean`, the lock gate `WaitWaiters` for concurrency, never a sleep) and its Ref tracking under `^OcuTalonTest("Approval")`. They answer as the README account `ocutalon` (holds `OcuTalonUser`), create no IRIS user, and keep no `ApprovalRequest` object across a hold's change. `ProbeSink`'s calls carry the row's `State` as an eighth element.
- Role, user, security and Workflow changes and test runs happen only on throwaway stacks through `ci/iris.sh` and `ci/warm.sh`; the developer slot is load-and-compile only. Tests restore every security object, setting and public key they change. Lane A extends the CI model mock only under `ci/mock/scenarios/A/`.

## UX & Interaction Patterns

- **Denials are plain sentences the model relays.** The model sees AI Hub's prefix ending "Tool access denied: " before each sentence, so sentences start in lower case, end with a period and read well after it; each is a gate class parameter, and the sentences stay distinct. A held call: `HELD`, "held for your approval; nothing was run.". An untrusted or tainted turn: only read-only tools can run, and the model describes the action as an offer the user can ask for in their own turn.
- **Answer statuses:** `Answer`'s results and `winner` feed channel statuses such as "Approved from Telegram at 14:15" and "Already answered: …". The bridge never renders user-facing text.
- **The turn indicator** shows the tool's readable label from `turn.step`; a label never holds arguments or model text.
