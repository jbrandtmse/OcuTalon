# Architecture Notes: OcuTalon

These notes support `ARCHITECTURE-SPINE.md`. They hold the evidence behind the spine's AI Hub choices, where the spine departs from the PRD addendum, the answers to the open items, the verdicts on the UX's handoff, and the PRD changes proposed to the author. The spine binds the build; these notes explain it. AD and spike ids match the spine.

## 1. The known AI Hub gaps, re-checked on build 154

Each gap was listed as known from the October 16 tests. It was re-checked against the build 154 class export and, where the behaviour lives in AI Hub's native library, against the running instance.

| Gap | Verdict on build 154 | Evidence | Design |
| --- | --- | --- | --- |
| Tool calls don't appear in Visual Trace | Holds | No `%AI` class references `Ens`; the agent loop runs every tool inside one native call; `EnsLib.AI.Agent.PassthroughOperation` produces one request and response per message, with an empty `ToolCalls` | The bridge records steps from AI Hub's hooks (AD-9) |
| AI Hub's vector table has no HNSW or full-text index | Holds | `%AI.RAG.VectorStore.IRIS` creates only a primary key; search is an exact cosine scan | Memory has its own table with HNSW and `%iFind` (AD-21) |
| Refusals have no server-side fallback | Holds | No fallback-model property or setting; the stop reason is only in `Response.Extra.finish_reason`; native retries cover 429, timeouts and connection errors only (S2) | The bridge's fallback route and the step-2 second-model retry (AD-8) |
| The Anthropic provider has no `base_url` | **No longer holds** | `%AI.Provider.%GetProviders()` on build 154 lists `base_url` for `anthropic`; `Create` forwards it. Tested end to end over HTTP and HTTPS (S3) | CI mock through `base_url`; the demo gateway too (AD-22, AD-25) |
| GPT-5 models reject `max_tokens` | Holds when a cap is set | The provider always sends `max_tokens` when given one; `extra_params` carries `max_completion_tokens` instead, which works (S2) | GPT-5 gets `max_completion_tokens` through `extra_params` (AD-7) |
| Config Store and MCP client untested | Config Store tested (S5); MCP client still untested | Descriptors, CRUD, `@{config:}` and the `<MCP><Stdio>` and `<MCP><Remote>` elements exist; no AI Hub code reads `AI.MCP` entries; a fresh instance needs `RebuildRegistry()` | S9 before step 4 |

**Other build 154 facts the spine relies on:**

- `EnsLib.AI.Agent.OutboundAdapter` exists, with production settings for the agent class, provider config, model, tools, skills, session config and the three policies. It builds the agent once per job and installs a policy only when its setting is filled. Policies added in code join a chain after those named in settings (S4), which is why OcuTalon's subclass adds its own and refuses the policy settings (AD-6, AD-10).
- Policies: Authorization `%CanExecute` runs before each tool call and may rewrite arguments; Audit `%LogExecution` and `%LogDenial` run after; Discovery `%Resolve` runs before each model request (experimental).
- `%AI.Agent.Session` is persistent with no owner field; its native state is per process, so it is re-attached on every turn.
- `timeout_ms` bounds the agent loop but is checked once per iteration, so the bridge's own timer is the hard bound (S2 confirmed it doesn't stop a request in flight).
- The adapter's `ProviderConfig` never supplies the model; with no `Model` setting and no `MODEL` parameter the provider default applies (S5 saw a larger model with a 131,072-token cap), so the spine keeps the model in the runner setting and the agent parameter (AD-7).
- `AutoCompactOnTokenLimit` acts only when the model's context window overflows (1M tokens for Haiku 5.5), so compaction forks and summarizes, guarded (AD-20).
- The knowledge base's search tool takes only `query` and `top_k`, with no filter, so per-session documents need separate knowledge bases (S14).
- `%AI.Utils.Template`'s `{{= }}` form runs code with the job's privileges; no OcuTalon instructions contain `{{` (AD-7).
- The Interoperability system user that production jobs run as holds `%All` on build 154 (AD-24's limits).
- The test instance runs the Community licence: 8 licence units and, the binding limit, 8 concurrent connections per instance (S13).
- On IRIS for Health, the namespace's Foundation portal application grants database roles to every signed-in user, so trace links use OcuTalon's own portal applications (AD-24).
- `Ens.Util.Tasks.Purge` can be limited to named configuration items (AD-27); `Ens.MessageHeader.ResendDuplicatedMessage` accepts a new body (AD-16); `EnsLib.Workflow` assignment requires a Workflow user (AD-11); `%SQL.Index.HNSW` and `%iFind` exist (AD-21).

**Spike results, October 17.** The first batch ran on the test instance, with throwaway classes, and on two disposable instances of the same build. Model behaviour that a real model can't be asked for (refusals, cut-offs, errors, rate limits, slow replies) was tested against a small stand-in for the model API, never by provoking the real model. Live calls were few and short.

## 2. Where the spine departs from the PRD addendum

| Addendum | Spine | Why |
| --- | --- | --- |
| §4: a business process calls the agent | `Decide` sends to a business operation on a subclass of AI Hub's outbound adapter (AD-6) | Uses AI Hub's own Interoperability adapter, keeps the process short, and makes the pool size the concurrency cap. S4 confirmed it on build 154, so the fallback (`Decide` calling the agent in its own job) isn't needed. Tools now run in the runner's job |
| §2: triage gets read-only tools plus notify and save-for-digest | Triage has no tools and answers with JSON (AD-7) | Cheaper, smaller injection surface, and build 154 has no structured-output API for Anthropic. An untrusted `act` runs a read-only turn in a fresh AI session (AD-30) |
| §14: the Dockerfile installs OcuTalon with IPM at build | IPM and the one `ocutalon` package install at container start, version-gated (AD-23) | The code database lives on the durable volume, so build time can't fill it, and an upgrade must recompile over the volume |
| §5: a scheduled job expires approval requests | `ApprovalHold`'s timer, plus an expiry check when an answer arrives (AD-11) | One waiter per request already exists; the answer-time check closes the race |
| §3 and §16: stand-in endpoints by host-name resolution | The Anthropic provider's `base_url`, over plain HTTP in CI (AD-22) | Build 154 declares `base_url` for Anthropic, and S3 confirmed it end to end |
| §9: forward alerts, or a 5 to 10 s watch service | A 3 s poller over message headers and the event log (AD-15) | Works on any production without changing it, and meets the 35-second typical target |
| §14: health check is IRIS running plus namespace ready | Also the installed version equals the image's (AD-23) | Catches an upgrade still compiling |

## 3. Answers to the open items

**The addendum's "to decide in architecture" table:**

| Item | Decision |
| --- | --- |
| The IRIS for Health template production | Leave it installed and stopped; OcuTalon's installer starts `OcuTalon.Production` after every install and upgrade, rather than autostart, so it never runs old code during an upgrade; never delete Foundation artefacts; never use the Foundation portal application for trace links (AD-3, AD-24) |
| The bridge as its own IPM module (Open Question 6) | Not within OcuTalon (the author, October 17): an Open Exchange listing carries one IPM package, so OcuTalon's one package contains the bridge and installs it itself. The bridge also loads on its own without IPM, a CI job proves it, and it becomes its own product with its own package and listing as a follow-on (AD-2) |
| Reacting within 15 seconds (FR-23) | A 3-second poller (AD-15) |
| Waiting reminders and approval requests across upgrades (FR-60) | Two frozen waiting-process classes, a row as the truth, and a startup reconciler (AD-5) |
| Durable storage or a plain container for judges | Durable `%SYS` and databases on a named volume (AD-23) |
| Plan B if CI can't mock the Anthropic path | Not needed: S3 confirmed Plan A, the Anthropic provider's `base_url` over plain HTTP (AD-22). Plans B (host alias plus private CA) and C (an OpenAI-provider mock) are dropped |

**The addendum's "to test" table:** every row is a spike: refusal and `max_tokens` surfacing and `output_config.effort` (S2), the non-Health image (S12), FastEmbed's cache with durable storage (S11), the MCP client and its policies (S9), `%AI.MCP.Service` and `iris-mcp-server` (S10).

**Online-demo capacity (S13):**
- **One live session per address: not adopted,** although S13 suggested it, because judges behind one office address would lock each other out. FR-15's limit of 5 new sessions per address per hour stays.
- **The remaining risk:** one address holding several places. AD-25 states it, with the idle cap and the runbook as the responses.

**Lane balance (decided by the author on October 17):** the installer's core (the step registry, the CPF merge file, the bootstrap, and the role, user, SSL, task, `Production` and `Public` steps) moved from Lane B to Lane A, which already owned the bridge installer. Lane A is now "platform and agent core", Lane B "experience" (AD-29). The October 26 checkpoint was superseded the same day, when the author moved Telegram to Lane A (AD-29).

**PRD open questions:** Q4 (MCP if AI Hub's client fails): settled by S9 as a split. AI Hub's client lists a server's tools; every call goes through OcuTalon's governed proxy tool and its own minimal client, which can cut results (AD-21). Q6 (the bridge as its own module): not within OcuTalon. One package contains and installs the bridge, which also loads on its own without IPM; its own package and listing are a follow-on (AD-2). Q1, Q3 and Q5 are the author's or later steps'; Q2 is settled by the evaluation set and one runner setting (AD-7).

## 6. The review gate

The draft spine went through eight independent reviews on October 16: reconciliation against the PRD, the addendum, the UX, and the brief with the internal notes; a rubric review; a check of every named technology against build 154 and the web; an adversarial review of the seams between the two build lanes; and a public-text and security review. Together they raised 7 critical and 59 high findings, almost all where the two lanes meet (who owns a message, a table or an event), plus online-demo security. The revised spine closes them with AD-30 to AD-33 and amendments to the other decisions; the review reports are not part of this repository.

A plan review then checked the final spine against UJ-1, the release 1 floor and the judging criteria, and approved it for epics on October 16. Its additions to S1, S7 and S13, the gateway's Telegram token swap, and four plan changes (Epic 0 time-boxed to October 21 to 23, polling before WebSocket, a lane checkpoint on October 26, and a tracked demo-host story due November 1) were accepted by the author and applied on October 17.
